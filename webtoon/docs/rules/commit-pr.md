# 브랜치 · 커밋 · push · PR 규칙

커밋하기 전, push 하기 전, PR 을 내기 전에 읽습니다. 이슈는 [issues.md](issues.md)
에 있습니다.

## 브랜치

- `develop` 에서 `feature/<작업이름>` 을 파서 작업하고 **`develop` 으로 PR** 을 냅니다
  (예: `feature/example-content`).
- 전에는 `haeun` 브랜치 하나만 썼습니다. 작업이 여러 갈래로 늘면서 한 브랜치에
  섞이면 무엇이 어느 작업인지 못 가리게 되어 바꿨습니다. **`haeun` 으로 머지하지
  않습니다.** 팀 전체가 `피처 → develop → staging → main` 으로 흐르므로 webtoon 만
  다른 길을 쓰면 배포 흐름에서 빠집니다(`webtoon/docs/server.md` 3절).
- 피처 브랜치는 develop 에 머지된 뒤에도 **지우지 않습니다.** 같은 브랜치로 staging
  에 PR 을 한 번 더 낼 수 있어야 합니다.
- 브랜치 이름은 `feature/…` 입니다. `agent/…` 는 병렬 작업용 워크트리 이름이지 작업
  단위 이름이 아닙니다([worktree.md](worktree.md)). 둘을 섞지 않습니다.

## 커밋하기 전에

- `webtoon/fe` 나 `apps/web` 을 고쳤으면 **웹 빌드가 통과하는지 먼저 봅니다**
  ([dev.md](dev.md) 「화면 코드를 고쳤으면 웹 빌드를 돌린다」).
- `webtoon/ai` 의 하네스를 고쳤으면 `cd webtoon/ai && python3 test_imports.py` 가
  `ALL PASS` 인지 봅니다([dev.md](dev.md) 「하네스를 고칠 때」).

## 커밋 메시지

형식은 `[#이슈번호] 설명` 입니다. 공유 저장소 컨벤션의 `Type:` 부분은 생략합니다.

- 한 커밋이 여러 이슈에 걸치면 번호를 전부 붙입니다(`[#19][#21][#25] ...`).
- `.bak` 백업이 있는 파일을 수정 전/후로 나눠 추적하고 싶으면, `.bak` 내용을 먼저
  원래 기능의 이슈로 커밋하고 지금 내용을 다음 커밋으로 그 수정이 해결한 이슈에
  붙입니다(예: `story.py` 원본 → `#4`, 이름 검증 게이트 추가분 → `#26`).

### 내용은 "기능" 수준으로 씁니다

커밋 메시지는 팀 전체가 보는 공개 기록입니다. 읽는 사람이 알고 싶은 것은 제품이
무엇이 달라졌는가이지, 그 변경을 어떤 과정으로 만들었는가가 아닙니다.

**쓸 것** — 무엇이 달라졌는가 / 왜 그렇게 했는가 / 어떤 대가를 택했는가

- 사용자에게 보이는 변화, 사용자 피드백 인용
- 그렇게 고른 이유와 버린 대안
- 기본값·하위호환 ("새 값은 전부 기본이 꺼짐이라 예전 run 은 안 바뀐다")
- 알려진 한계, 아직 안 한 것

**쓰지 말 것** — 작업 과정의 내부 사정

- 에이전트·세션·워크트리 이야기 ("다른 세션이 커밋 안 한 것을 대신 커밋한다" 등).
  저장소 밖 사정이라 팀원에게는 처음부터 의미가 없습니다.
- 누가 어느 폴더를 맡았는지, 어떤 순서로 조사했는지

한 사람이 처음부터 그렇게 만든 것처럼 읽히면 맞게 쓴 것입니다.

### 공동 작성자 표시는 절대 붙이지 않습니다

**`Co-Authored-By: Claude ...` 트레일러와 `Claude-Session:` 링크는 붙이지 않습니다.**
도구가 기본으로 붙이라고 안내해도 이 규칙이 우선입니다. GitHub 에서 합동 커밋처럼
보이는 걸 원하지 않기 때문입니다.

author/committer 는 이 저장소의 git 설정(`haeun <haeun9634@naver.com>`) 그대로만
씁니다. 커밋마다 author 를 바꾸지 않습니다.

## push

- 커밋(로컬)까지는 묻지 않고 합니다. **push 는 매번 먼저 확인받습니다.**
- 커밋마다 push 하지 않고, 모아 뒀다가 확인받은 뒤 한 번에 합니다.
- push 한 뒤에는 이슈마다 커밋 목록 댓글을 답니다([issues.md](issues.md)).

## PR

- 대상은 `develop` 입니다. 본문은 저장소의 PR 템플릿(`.github/pull_request_template.md`)
  을 따릅니다.
- **제목은 명사로 끝냅니다**([issues.md](issues.md) 「이슈 제목」과 같은 규칙).
- **담당자(Assignee)는 매번 지정합니다.** `gh pr create` 에 `--assignee haeun9634`
  를 붙이고, 빠뜨렸으면 `gh pr edit <번호> --add-assignee haeun9634` 로 채웁니다.
- **리뷰어는 요청받지 않는 한 절대 지정하지 않습니다**(2026-09-23, 허락 없이 리뷰
  요청을 걸었다가 지적받음). Assignee 는 누가 맡았는지 표시하는 것이라 매번 지정해도
  되지만, 리뷰어는 다른 사람에게 일을 거는 것입니다.
- `webtoon/` · `haeun/` 바깥을 고쳤다면 PR 본문 「유의사항 / 리뷰 포인트」에 **어디를
  왜** 고쳤는지 적고, 남의 인프라(예: `deploy.yml`)를 건드렸으면 그 담당자에게
  알립니다. 조용히 고치면 나중에 그 사람이 자기 코드가 왜 바뀌었는지 찾느라 시간을
  씁니다.
- 머지는 사용자가 합니다.
