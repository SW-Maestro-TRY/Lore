# 저장·파기 규칙

사용자 데이터와 그림을 어디에 두고, 언제 누가 지우는지 정리한 문서입니다. 숫자는
`common/be/.../retention/RetentionPolicy.java` 와 개인정보처리방침 제4조가 원본이고,
여기는 그 둘을 운영 관점에서 묶어 본 것입니다(2026-10-27 기준).

## 원칙

1. **사용자 그림은 앱이 DB 기록을 보고 지웁니다.** S3 버킷 규칙으로 날짜만 보고 지우지
   않습니다. 그림 이름이 무작위(`images/webtoon/<uuid>`)라서, 살아 있는 작품의 그림과 지운
   작품의 그림을 버킷은 구분하지 못합니다.
2. **버전 관리는 꺼 둔 채로 둡니다.** 켜면 지운 파일이 옛 버전으로 남아 "탈퇴 후 30일 삭제"를
   지킬 수 없습니다. 되살리기는 앱 휴지통이 맡습니다.
3. **사용자 데이터가 들어간 사본(백업·스냅샷·로그·외부 추적)에는 모두 기한을 둡니다.** 그
   기한은 처리방침에 적고, 적은 대로 지킵니다.

  `environment:` 둘 다에 이름을 넣어야 들어갑니다(`server.md` 4-2).
- 오래 접속하지 않은 계정을 정리하는 규칙은 없습니다. 만들려면 처리방침부터 고칩니다.

### 옛 그림 대기열 (`webtoon_art_discard`)

그림은 올릴 때마다 새 이름을 받고 DB 에는 지금 쓰는 이름만 남습니다. 그래서 이름이 바뀌는
순간 옛 이름을 놓치면, 작품을 지우거나 탈퇴해 파기해도 옛 판은 S3 에 영원히 남습니다
(파기는 DB 에 적힌 이름만 지웁니다).

- 이름이 바뀌는 자리(`PageStore.record` · `BakeService` 다시 굽기 · 구운 장 거두기)가 옛 이름을
  대기열에 적습니다.
- 7일 뒤 `ArtDiscardSweep` 이 웹툰 표(장·구운 장·캐릭터·조연 시트·올린 사진)를 다시 보고,
  아무 데서도 안 쓰면 S3 에서 지우고 대기열에서 뺍니다. S3 를 못 지우면 줄을 남겨 다음 날 다시
  지웁니다.
- 로컬(버킷 없음, 또는 창고가 `localhost`)에서는 지우지 않습니다. 바꾸려면
  `lore.webtoon.art-discard.keep`(true/false).

### 이미 쌓인 주인 없는 그림 — 관리자 점검

대기열을 만들기 전에 쌓인 옛 그림은 관리자 점검으로 찾습니다(2026-10-27 운영: 창고 21,213장,
DB 가 아는 주소 2,274개).

```
GET  /api/webtoon/v1/admin/storage/orphans   # 세기만 한다
POST /api/webtoon/v1/admin/storage/orphans   # 같은 기준으로 찾은 것을 대기열에 적는다
```

- 기준: `images/webtoon/` · `private/webtoon/` 아래 파일 가운데, **DB 의 어느 글자 칸에도** 그
  주소가 없고(`ArtReferences` 가 모든 표의 문자열·JSON·배열 칸을 훑음), 올라온 지 2일이 지난 것.
- 표를 정해 두지 않고 DB 전체를 훑는 이유: 정해 둔 목록에서 하나만 빠져도 살아 있는 그림을
  지우게 됩니다. 한 칸이라도 못 읽으면 아무것도 안 적고 멈춥니다.
- 넣기(POST)를 해도 바로 지우지 않습니다. 7일 뒤 정리 작업이 다시 확인하고 지웁니다.
- 쓰는 순서: GET 으로 수와 예시를 보고 → 예시 주소 몇 개가 실제로 어디에도 안 쓰이는지 화면에서
  확인하고 → POST.
