# 전체 검수 AI 설계 (2026-09-16)

`pagecheck.py`(장 단위 검수)와는 별개로, **완성된 화 전체를 다시 읽는 검수**를
새로 설계하는 중이다. 예전에 있던 `episodecheck.py`(블라인드 읽기 + 견주기,
2회 호출)는 "못 잡는 것 같다"는 판단으로 2026-09-16에 코드를 통째로 지웠다
(`run.py`·`llm.py`·`JobRunner.java`·`prompt/blind_read_prompt`·
`prompt/episode_review_prompt` 전부 제거, `git log` 참고).

## 진행 상태

- **1단계(판정만) — 구현 완료.** `fullreview.py` · `prompt/full_review_prompt`
  · `llm.py`의 `FULL_REVIEW` 스테이지. 이슈마다 `rank`(어디서 발견했는지)
  ·`severity`(critical/major/minor)·`redraw`(true/false)·`redraw_pages`·
  `why`를 받고, 모델이 규칙을 어겨도(5·6순위인데 critical, major인데
  redraw:true) `fullreview.parse()`가 코드로 강제한다.
- **2단계(재생성 루프) — 구현 완료 (2026-09-16).** §6에 정리한 설계 그대로
  `JobRunner.java`의 `runFullReviewLoop()`가 오케스트레이션을 맡는다.
  `run.py`는 더 이상 화 전체 검수를 스스로 트리거하지 않는다 — 그리기가
  끝나면 항상 자바가 `--full-review`를 부른다(`pages()` → `drawPages()`/
  `drawInOneProcess()` 다음, `stitch` 전). `--full-review` CLI 플래그
  자체는 단독 실행용으로 남아 있다.

## 1. 왜 페이지 검수와 별개로 있어야 하는가

지금 남아 있는 `pagecheck.py`(PAGE_REVIEW)는 그림 한 장을 그릴 때마다
**직전 장과 지금 장 두 장만** 보고 "이어지는가"를 판정한다. 구조상 이것으로
못 잡는 문제가 있다.

- **장거리 문제** — 인접한 두 장은 매끄러운데, 10페이지 전에 있었던 상태와
  지금이 어긋나는 경우. 두 장만 보는 검수는 "10페이지 전"을 볼 방법이 없다.
- **누적 반복** — 3페이지 전에 이미 지나간 상황을 다시 보여주는 것. 직전
  한 장만 보면 "이어짐"으로 통과한다.
- **전체 독서 경험** — 페이지 하나하나는 각각 이해돼도, 처음부터 끝까지
  읽었을 때 "왜 이렇게 됐지?"가 생기는 경우.

그래서 **완성된 화 전체를 1페이지부터 마지막까지 순서대로 읽는 별도 검수**가
필요하다는 것이 이번 설계의 출발점이다.

## 2. 역할 정의 — 페이지 검수 vs 전체 검수

```
페이지 검수 (pagecheck, 이미 있음)          전체 검수 (새로 설계 중)

직전 페이지                                Page 1 → 2 → 3 → ... → N
    ↓                                          ↓
현재 페이지                            전체를 독자처럼 처음부터 읽음
    ↓                                          ↓
"이 페이지가 맞는가?"                  "이 페이지들이 모였을 때
                                          이야기가 맞는가?"
```

> 페이지 검수는 **현재 페이지의 정확성**을 검사하고,
> 전체 검수는 **페이지들이 연결된 결과물의 정확성**을 검사한다.

전체 검수 AI는 그림을 다시 심사하는 사람이 아니다. "이 페이지가 잘
만들어졌는가"는 이미 페이지 검수에서 끝난 일이고, 전체 검수는 오직 "이
페이지들을 이어서 읽었을 때 이야기가 무너지는가"만 본다.

## 3. 중복 제거 기준 — "같은 것을 다시 보는가"가 아니라 "같은 대상을 다른 범위에서 보는가"

같은 단어(연속성·화자·대사)를 쓰더라도 **범위가 다르면 중복이 아니다.**
범위가 같으면 중복이니 전체 검수에서 뺀다.

| 항목 | 페이지 검수 | 전체 검수 | 전체 검수에서 |
|---|---|---|---|
| 장면 구현 | 이 페이지가 자기 scene을 표현했는가 | 전체 맥락 속에서 그 장면이 이해되는가 | **다시 봄** (관점이 다름) |
| 페이지 스토리 전달 | 이 페이지 장면이 이해되는가 | 순서대로 읽었을 때 전체 이야기가 이해되는가 | **범위를 바꿔서 봄** |
| 말풍선 화자 | 이 페이지 안에서 화자가 맞는가 | — | **원칙적으로 안 봄** (전역적 모순만 예외) |
| 대사 자연스러움 | 이 장면에서 어색하지 않은가 | — | **안 봄** |
| 대사 모순 | (안 봄) | 앞뒤 페이지의 사실관계가 충돌하는가 | **다시 봄** |
| 페이지 연결 | 직전 페이지와 이어지는가 | 전체 누적 상태와 일관되는가 | **다시 봄** (직전 1장이 아니라 누적) |
| 반복 | 직전 페이지와 같은 순간인가 | 여러 페이지 전과 같은 순간으로 돌아갔는가 | **다시 봄** (장거리 반복은 페이지 검수가 못 잡음) |
| 인물/공간/시간 연속성 | 직전 페이지 대비 | 작품 전체 누적 상태 대비 | **다시 봄** |
| 컷 폭/간격 | 참고 수준 | 구간 전체가 튀는가 | 필요할 때만, 항상 경고 |
| 세로형 여부 | 이 페이지가 세로형인가 | 작품 전체가 세로 스크롤로 유지되는가 | 전체 구조로 다시 봄 |
| 웹툰형 연출·효과음 | 이 장면에 있는가 | 작품 전체 밀도가 부족한가 | 전체 수준만, 항상 경고 |
| 작화·채색 품질 | 안 봄 | 안 봄 | **안 봄** |

**원칙**: 페이지 검수가 이미 확정한 "페이지 내부" 판단(꼬리 위치, 그 장면
대사가 자연스러운가, 효과음 유무, 컷 구성·여백·배경 디테일, 세로형 여부
자체)은 전체 검수에서 재검사하지 않는다. 전체 검수는 **여러 페이지를 동시에
봐야만 드러나는 문제**에만 집중한다.

## 4. 검사 항목 — 우선순위 6단계

```
1순위 ★★★★★  장거리 스토리 연속성 — 설명 없는 단절
2순위 ★★★★★  이야기 진행 — 반복 / 제자리걸음 / 중요 사건 누락
3순위 ★★★★☆  전체 이야기 이해 가능성 — 처음부터 끝까지 따라갈 수 있는가
4순위 ★★★☆☆  전역 일관성 — 인물·대사·사건 상태가 작품 전체와 모순되지 않는가
5순위 ★★☆☆☆  전체 시각적 연속성 — 컷 폭·간격·톤이 구간 전체로 튀는가
6순위 ★☆☆☆☆  전체 웹툰 독서 경험 — 세로 스크롤·연출 밀도·효과음 밀도
```

**우선순위(rank)는 등급(severity)이 아니다.** 처음에는 "1~4순위 =
재생성, 5~6순위 = 항상 경고"로 순위를 곧 등급으로 썼는데, 같은 순위
안에서도 심각도가 갈린다는 지적으로 분리했다(2026-09-16) — 예를 들어
1순위(장거리 연속성) 안에서도 "장소가 약간 튀지만 맥락상 유추 가능"은
낮은 심각도고, "장소가 갑자기 바뀌어 이야기를 이해할 수 없다"는 높은
심각도다. 지금 구조는 이렇다.

- **순위(rank, 1~6)** — 어디를 보다가 발견했는지. 검사 항목 분류일 뿐,
  심각도가 아니다.
- **심각도(severity)** — critical / major / minor 3단계. 1~4순위에서만
  critical이 나올 수 있다(5~6순위는 이야기 이해와 무관한 항목이라
  구조적으로 critical이 될 수 없다 — 코드가 강제한다, §6.4 참고).
- **재생성 대상인가(redraw)** — severity와 별개의 값. critical이면
  원칙적으로 true지만, 페이지 하나를 다시 그린다고 해결 안 되는 구조적
  문제라면 critical이어도 false로 둘 수 있다. major·minor는 redraw가
  항상 false다(코드가 강제한다).

핵심 판단 기준은 한 줄로 수렴한다: *"처음 페이지부터 마지막 페이지까지
실제 독자처럼 읽었을 때, 흐름이 끊기거나 반복되거나 중요한 사건이 사라져서
독자가 혼란스러워지는 부분이 있는가?"*

### 반복 판정의 함정 — "비슷한 그림 ≠ 반복"

같은 행동이 여러 페이지 이어져도 **매 페이지 상황이 실제로 달라지면
정상**이다(도망 장면이 3페이지 이어져도 쫓기는 거리·장소·위기감이
바뀌면 진행이다). 반복으로 잡는 것은 **같은 행동이 이어지는데 실제
정보·사건 진행이 없는 경우**뿐이다.

### "장소·시간이 바뀌었다" 자체는 문제가 아니다 — "설명 없는 전환"만 문제다

페이지 사이에 시간이 지나거나 장소가 바뀌는 것 자체는 당연히 가능하고
정상이다. 예를 들어 "이미지 1: 교실 → 이미지 2: 카페"는 그 자체로는
아무 문제가 없다 — "수업이 끝난 뒤 친구를 만나러 카페로 향했다"는
나레이션 한 줄이면 충분히 설명된 것이다. 문제는 **변화 자체가 아니라,
설명되지 않은 전환 때문에 이야기 연결이 끊기는 경우**뿐이다("교실에서
대화 중 → 아무 설명 없이 병원에 누워 있음"처럼 독자가 "왜 여기
있지?"라고 느끼는 경우).

이 구분을 프롬프트에 명시적으로 못 박아 두지 않으면 "장소가 바뀌었으니
불일치 → critical" 같은 기계적 판정으로 샐 수 있다는 지적이 있어서,
`prompt/full_review_prompt`의 1순위 절에 위 교실→카페 예시를 그대로
넣고 "장소·시간의 변화 자체를 문제로 판단하지 마라"는 문장을 명시적으로
추가했다(2026-09-16).

## 5. redraw 대상 페이지를 어떻게 정하는가

두 페이지의 상태가 충돌했을 때 원칙은 **더 나중에 나온 페이지를 redraw
대상으로 지정**한다(먼저 나온 페이지는 그 이전 흐름과 이미 맞물려 확정된
것으로 본다).

예외적으로 **앞쪽 페이지**를 지정하는 경우:

- 나중 페이지가 이미 그 뒤 여러 페이지와 맞물려 있어서, 나중 페이지를
  고치면 오히려 그 뒤 페이지들과 새 충돌이 생기는 경우.
- 앞쪽 페이지의 문제가 명백한 단순 실수이고, 고쳐도 그 이후 흐름에
  영향이 없는 경우.

이 예외를 쓸 때는 **어느 쪽을 골랐는지와 그 이유를 한 줄로 남긴다.**

## 6. 재생성 루프 설계 (2단계 — 구현 완료, 2026-09-16)

페이지를 재생성했으면 **그 페이지는 다시 페이지 검수(pagecheck)부터
거치고, 통과하면 그 다음에 전체 검수를 다시 돈다.** 이 루프는 품질을
올리는 동시에 **과금과 무한루프 문제를 같이 만들 수 있어서**, 설계·
책임 경계부터 정하고 나서 코드를 썼다. 실제 구현은
`JobRunner.java`의 `runFullReviewLoop()`/`redrawPage()`/
`readFullReview()`다 — 아래 6.1~6.5는 그 구현이 그대로 따른 설계고,
각 절 끝에 실제 구현이 설계와 다르게 간 지점이 있으면 적어 둔다.

### 6.1 오케스트레이션은 자바(JobRunner), 파이썬은 실행 단위만

파이썬 쪽에 상태 머신을 넣지 않는다. 각 스크립트는 "한 가지 일"만 하고
끝낸다 — 몇 번째 시도인지, 이번 재생성이 허용되는지, 다음에 뭘 해야
하는지는 전혀 모른다.

```
fullreview.py  → 판정 결과만 낸다 (누구를 다시 그릴지는 자기가 안 정한다)
pagecheck.py   → 재생성된 페이지 하나의 판정만 낸다
run.py         → 시킨 페이지를 실제로 그리기만 한다
```

**언제·누구를 다시 그릴지, 몇 번째 시도인지, 한도를 넘었는지, 최종적으로
사람에게 넘길지** 같은 워크플로 상태는 전부 `JobRunner.java`가 쥔다 —
이 저장소에서 이미 그렇게 하고 있는 것(줄 세우기·취소·재시도)과 같은
층이라 자연스럽다.

```
              ┌──────────────┐
              │  fullreview  │
              └──────┬───────┘
                     │ redraw_pages (critical만)
                     ▼
            ┌─────────────────┐
            │  JobRunner.java  │  ← 루프·승인·한도를 여기서 관리
            └────────┬─────────┘
                     │
              페이지 재생성 (run.py --detail-pages --page N)
                     │
                 pagecheck
                     │
          ┌──────────┴──────────┐
          │                     │
        통과                  또 걸림
          │                     │
          ▼                     ▼
     fullreview 재실행    페이지별 재시도 한도 확인
                                │
                    한도 안 → 다시 재생성
                    한도 넘음 → 그 페이지는 포기, 사람에게 넘김
```

**실제 구현 노트**: 다이어그램의 "페이지 재생성 → pagecheck"는 자바가
따로 두 번 부르는 게 아니다. `run.py --detail-pages --page N`
호출 하나 안에서 `detailart.draw_continue`의 기존 재시도 루프가
그 페이지를 그리고 곧바로 `pagecheck`까지 같이 돈다(§full-review 이전에
이미 있던 pagecheck 구조, 기본 1회 자동 재시도). `JobRunner`는 이
호출 하나만 하고 결과(성공/실패)만 본다 — pagecheck를 별도로 부르는
코드는 없다.

### 6.2 한도 — "전체 라운드"보다 "페이지별 횟수"가 우선

- **페이지별 재생성 최대 2회.** fullreview가 라운드마다 다른 페이지를
  지목할 수 있어서(1차 `[7,12,18]` → 2차 `[7]` → 3차 `[12]`처럼), 전체
  라운드 수만으로는 "이 페이지가 몇 번 고쳐졌는지"를 못 잰다. 페이지
  단위로 따로 세야 한다.
- **전체 fullreview 라운드도 별도 상한(예: 3회)** 을 둔다 — 페이지별
  한도를 넘기 전에 라운드 자체가 끝없이 늘어지는 것을 막는 안전장치.
- 페이지별 한도를 넘겼는데 그 페이지가 여전히 걸리면: 그 페이지만
  "자동 수정 실패"로 접고 사람에게 넘긴다. 다른 페이지는 계속 루프를
  돈다(한 페이지가 멈춘다고 전체가 멈추지 않는다).

**2026-09-16에 반영 완료.** `JobRunner.MAX_FULL_REVIEW_ROUNDS = 3`,
`MAX_PAGE_REDRAWS = 2`. `runFullReviewLoop()`가 페이지별 카운터
(`Map<Integer, Integer> redrawn`)를 라운드 밖에서 들고 있다가, 한도를
넘긴 페이지는 그 라운드의 재생성 대상에서 빼고(`gaveUp`) 나머지만
계속 돈다 — 한 페이지가 한도에 걸려도 다른 페이지는 안 멈춘다.

### 6.3 승인 — "라운드 수를 사전에 일괄 승인"

`webtoon/CLAUDE.md`의 "실제 과금이 걸리는 실행은 항상 먼저 승인받는다 ·
한 번 승인받았다고 다음 것까지 승인된 게 아니다" 원칙과 이 루프가
충돌하지 않으려면, **승인 대상을 "각 재생성 1건"이 아니라 "이 루프
전체를 최대 N라운드까지"로 잡는다.**

- 사용자가 (또는 서비스 정책이) 미리 "자동 수정 최대 N라운드까지 허용"을
  승인하면, 그 한 번의 승인으로 라운드 1~N까지는 자동으로 돈다.
- **승인된 라운드를 넘어서는 순간 무조건 멈춘다** — 넘겨서 계속 돌려면
  그건 새 승인이다(기존 "한 번 승인이 다음 것까지 승인은 아니다" 원칙
  그대로).
- 한도 안에서 다 못 고치면: 자동 수정을 종료하고 **남은 문제 목록(페이지
  + 사유)을 사람에게 그대로 보여준다.** 조용히 포기하지 않는다.

**2026-09-16에 반영 완료 — 다만 "보여준다"는 두 층으로 나뉜다.**

- **만드는 도중(실시간)**: `JobProgress`(기존에 STORY·SHEET 단계에서
  "루가 …하고 있어요"를 보여주던 바로 그 채널)에 `progress.say(...)`로
  "루가 이야기가 잘 이어지는지 처음부터 다시 읽고 있어요" → "검수에서
  걸린 N페이지를 다시 그리고 있어요" → (한도 도달 시) "루가 최대한
  다듬었어요 — 일부는 더 못 고쳤지만 완성으로 넘어가요"가 그대로
  뜬다. FE 코드는 안 고쳤다 — `Progress.tsx`가 `job.say`를 그대로
  렌더링하는 구조라 자동으로 뜬다.
- **다 만든 뒤(완성본 화면)**: 아직 없다. `RunService`는 "하네스 폴더를
  안 읽는다"는 걸 의도적으로 지켜 온 곳이라(그 폴더는 서버 재시작·
  worktree 정리로 없어질 수 있는 작업대지라, 클래스 문서에 이유가
  명시돼 있다), `full_review.json`을 완성본 화면에서 그때그때 읽어
  보여주는 건 그 원칙과 부딪힌다. 영구히 남기려면 DB 칼럼이 필요하고,
  새 마이그레이션은 `apps/api/src/main/resources/db/migration`에
  넣어야 하는데 그 경로는 이 세션의 자유 편집 범위 밖(`webtoon/`·
  `haeun/` 바깥)이라 **먼저 확인받아야 한다** — §7에 남겨 둔다.

### 6.4 자동 재생성은 critical만 — major/minor는 기록만

과금 대비 효율을 가르는 기준으로 심각도를 쓴다.

| 심각도 | 자동 루프에서 |
|---|---|
| critical (독자가 이야기를 못 따라감) | 재생성 후보 |
| major (개선하면 좋지만 이해에 지장 없음) | 기록 + 사람에게 보여줌 (재생성 안 함) |
| minor | 기록만 |

**2026-09-16에 반영 완료.** `prompt/full_review_prompt`·`fullreview.py`가
이슈마다 `severity`(critical/major/minor)와 `redraw`(true/false)를
따로 받고, 모델이 규칙을 어겨도(5·6순위인데 critical로 내거나, major인데
redraw:true로 내는 경우) `fullreview.parse()`가 코드로 한 번 더 눌러서
위 표를 강제한다. `JobRunner.runFullReviewLoop()`는 이슈마다 `issue.path
("redraw").asBoolean(false)`가 참인 것만 재생성 대상으로 모은다 — major·
minor는 `redraw`가 항상 false로 내려오므로 이 필터를 그냥 통과 못 하고
걸러진다(자동으로는 아무 그림 값도 안 나간다).

### 6.5 재생성 지시에는 "무엇이 문제인지"가 같이 가야 한다

`redraw_pages`가 페이지 번호만 갖고 있으면 안 된다. 페이지 번호만
받아서 "이 페이지를 다시 그려라"라고 하면, 다시 그리는 모델이 엉뚱한
부분(의상·대사·다음 페이지와의 관계)까지 바꿔서 **한 문제를 고치다
다른 문제를 새로 만드는 핑퐁**이 생길 수 있다. 그래서 재생성 지시에는
반드시 다음이 같이 가야 한다.

- 어느 페이지들이 충돌했는지 (예: 6페이지와 7페이지)
- 무엇이 문제인지 (예: "6페이지에서 문을 발견한 직후인데 7페이지는 이미
  숲으로 이동해 있어 이동 과정이 설명되지 않음")
- **문제 해결에 필요한 부분만 바꾸고, 그 페이지의 나머지(정상적으로
  이어지던 인물·대사·연출)는 최대한 유지하라**는 지시. 이 원칙이 없으면
  한 문제를 고치다 다음 페이지와 또 안 맞는 새 문제가 생긴다.

**2026-09-16에 반영 완료 — 끝까지.** `prompt/full_review_prompt`의 `why`
필드가 "무엇만 고치고 무엇은 유지해야 하는지"를 담아 나오고,
`JobRunner.redrawPage()`가 그 `why` 텍스트를 그대로 `--note`로 넘긴다.
`run.py --detail-pages --page N --note <why>`가 그 값을
`detailart.note_block()`로 그리는 프롬프트 뒤에 붙인다(기존 편집실
다시그리기와 같은 자리) — 재생성 프롬프트가 "무엇이 문제인지"를 그대로
받는다. 같은 페이지가 이슈 여러 개에 걸리면 `why`를 줄바꿈으로 이어
붙인다(`runFullReviewLoop`의 `target.merge`).

## 부록 — 프롬프트 (사용자 작성 원안, 2026-09-16)

아래는 위 설계를 바탕으로 사용자가 직접 작성한 판정 기준 원문이다.
**실제로 `prompt/full_review_prompt`에 파일로 있고 `fullreview.py`가
그대로 부른다** — 판정 기준(우선순위 6단계·등급 규칙·재생성 대상 지정
규칙) 문장은 원안과 똑같다.

실제 파일은 원안에서 두 곳이 달라졌다 (둘 다 2026-09-16, 아래 원안
텍스트는 그 전 버전이라 최신 상태와 어긋난다).

1. 원안의 `[출력]` 절은 사람이 읽는 문장 형식
   (`[등급: 재생성/경고] [해당 페이지 범위]` ...)이었는데, 실제 파일에서는
   **JSON 출력**으로 바꿨다 — `redraw_pages`를 코드가 읽어서 나중에(§6)
   자동 재생성 루프에 넘기려면 구조화된 값이 있어야 해서다.
2. 원안은 등급이 `재생성`/`경고` 이진값이었는데, 실제 파일은 §4·§6.4에서
   정리한 대로 **순위(rank)와는 별개로 `severity`(critical/major/minor)
   와 `redraw`(true/false)를 따로 받는다.** 또한 "장소·시간이 바뀌었다"
   자체를 문제로 오인하지 않도록 1순위 절에 교실→카페 예시와 명시적
   금지 문장을 추가했다(§4 참고).

실제 파일 원문은
`webtoon/ai/new_harness/prompt/full_review_prompt`를 보는 게 정확하다
(여기 아래 내용은 그 파일을 만들 때 쓴 원안이라 최신 상태가 어긋날 수
있음).

```
이 AI의 역할은 완성된 웹툰 전체를 1페이지부터 마지막 페이지까지
독자처럼 순서대로 읽으면서, 페이지 각각의 완성도가 아니라
페이지들이 모였을 때 이야기가 맞는지를 검사하는 것이다.

너는 그림을 다시 심사하는 사람이 아니다.
너는 "이 페이지가 잘 만들어졌는가"를 보지 않는다.
그건 이미 페이지 검수 단계에서 끝난 일이다.
너는 오직 "이 페이지들을 이어서 읽었을 때 이야기가 무너지는가"만 본다.

[입력]
전체 페이지가 순서대로 주어진다. 각 페이지는 이미지와
(있다면) 대사·나레이션 텍스트를 포함한다.

[절대 다시 보지 않는 것]
아래 항목은 페이지 검수에서 이미 확정된 것으로 간주하고
너는 재검사하지 않는다. 개별 페이지 안에서 이런 문제가
보여도 지적하지 마라. 그건 네 담당이 아니다.

- 개별 페이지의 작화 품질, 얼굴/신체 형태
- 개별 페이지의 말풍선 꼬리 위치(그 페이지 안에서 맞는지)
- 개별 페이지의 대사가 그 장면에서 자연스러운지
- 개별 페이지의 효과음 유무
- 개별 페이지의 컷 구성, 여백, 배경 디테일
- 개별 페이지가 세로형인지 자체

[네가 봐야 하는 것 — 우선순위 순]

1순위. 장거리 스토리 연속성
페이지를 여러 장 넘기면서 생기는 단절을 찾는다.
바로 옆 페이지끼리는 자연스러워 보여도, 그 전에 있었던
장면이나 상태와 어긋나면 잡아야 한다.
예: 20페이지 전에 이미 통과한 문을 지금 처음 발견한
것처럼 그려짐.
장소나 시간이 바뀔 때, 나레이션이나 장면으로 그 이유가
설명되면 정상이다. 아무 설명 없이 바뀌면 문제다.
판정: 설명 없는 단절 → 재생성 대상 페이지 지정.
설명이 빈약하지만 맥락상 유추 가능 → 경고.

2순위. 이야기 진행 / 반복 / 누락
아래 세 가지를 각각 구분해서 본다.

- 같은 순간의 반복: 여러 페이지 전에 있었던 것과 같은
  행동·상태로 되돌아가 있는데 그 사이 아무 진행이 없다.
  (예: 10페이지 전에 이미 지나간 상황을 다시 보여줌)
  같은 행동이 이어져도 사건이 실제로 진행되고 있으면
  반복이 아니다. (도망치는 장면이 3페이지 이어져도
  매 페이지 상황이 달라지면 정상.)
- 제자리걸음: 여러 페이지에 걸쳐 아무 정보도 사건도
  진전되지 않음.
- 중요 사건 누락: 이야기 이해에 꼭 필요한 사건이
  중간에 통째로 빠짐. (칼을 발견하는 장면 없이
  갑자기 누가 칼에 찔림)
판정: 반복/제자리걸음/누락으로 독자가 "왜 그대로지?"
"이게 왜 갑자기 일어났지?"라고 느낄 정도 → 재생성.
약간 늘어지는 정도 → 경고.

3순위. 전체 이야기 이해 가능성
처음부터 끝까지 순서대로 읽었을 때, 지금 무슨 일이
벌어지고 있는지 계속 따라갈 수 있는가를 본다.
개별 페이지는 각각 이해돼도 이어 놓았을 때 "왜 이렇게
됐지?"가 생기면 문제다.
그림, 대사, 나레이션이 합쳐져서 하나의 이야기로
읽히는지도 여기서 본다.
판정: 특정 구간을 이해할 수 없어 이야기를 따라가지
못하게 됨 → 재생성. 약간 헷갈리지만 뒤에서 이해됨 → 경고.

4순위. 전역 일관성 (인물 / 대사 / 사건 상태)
직전 페이지가 아니라 작품 전체에 걸쳐 누적된 상태와
비교한다.
- 인물: 외형, 소지품, 관계가 설명 없이 바뀌지 않았는가.
- 대사: 앞에서 한 말과 뒤에서 한 말이 사실 관계에서
  충돌하지 않는가. (예: "처음 봐" ↔ "어릴 때부터 친구")
- 사건: 이미 해결된 일이 다시 미해결로 나오거나,
  아직 안 일어난 일이 먼저 등장하지 않았는가.
- 화자: 특정 페이지의 대사가 나중에 보니 다른 인물이
  한 것처럼 모순되지 않는가. (개별 말풍선 위치가 아니라
  이런 전역적 화자 모순만 본다.)
판정: 사실관계 충돌로 설정이 무너짐 → 재생성.
사소한 변화나 애매한 경우 → 경고.

5순위. 전체 시각적 연속성
컷 폭, 간격, 톤이 페이지마다 크게 튀어서 작품 전체가
하나로 안 느껴지는가를 본다. 개별 페이지의 미세한
차이는 신경 쓰지 말고, 구간 전체가 확 달라지는 경우만
잡는다.
판정: 항상 경고. 재생성 대상 아님.

6순위. 전체 웹툰 독서 경험
- 세로 스크롤 흐름이 작품 전체에서 유지되는가
  (일부 페이지만 가로형으로 튀는 경우)
- 그림만 있고 말풍선/나레이션/효과음이 거의 없는
  구간이 있어 전체적으로 밋밋한가
- 사건에 비해 효과음이 작품 전체적으로 부족하게
  느껴지는가
판정: 항상 경고. 재생성 대상 아님.

[등급 기준 요약]
재생성: 독자가 이야기를 이해하거나 따라가는 데
        실제로 지장이 생기는 문제. (1~4순위에서만 발생)
경고: 이해에는 지장 없지만 개선하면 더 좋아지는 것.
      (5~6순위는 항상 경고, 1~4순위의 애매한 경우도 경고)

[출력]
구간별로 발견한 문제만 나열한다. 문제가 없는 페이지는
언급하지 마라.

형식:
[등급: 재생성/경고] [해당 페이지 범위]
- 순위 항목:
- 무엇이 문제인가 (구체적으로, 어느 페이지의 어떤 상태와
  어느 페이지의 어떤 상태가 충돌하는지)
- 재생성이라면: 어느 페이지(들)를 다시 만들어야 문제가
  해결되는지 명시

전체를 다 읽었는데 문제가 하나도 없으면
"전체 검수 통과"라고만 답하라.

[재생성 대상 지정 규칙]
문제가 두 페이지 이상의 충돌로 발생했을 때, 재생성 대상은
원칙적으로 더 나중에 나온 페이지다.
(예: 5페이지의 상태와 30페이지의 상태가 충돌하면,
30페이지를 재생성 대상으로 지정한다. 5페이지는 이미
그 이전 흐름과 맞물려 확정된 것으로 본다.)

단, 다음의 경우는 예외로 앞쪽 페이지를 지정한다:
- 나중 페이지가 이미 그 이후의 여러 페이지와 맞물려
  진행되고 있어, 나중 페이지를 고치면 오히려 그 뒤
  페이지들과 새로운 충돌이 생기는 경우
- 앞쪽 페이지의 문제가 단순 실수로 보이고
  (예: 명백히 잘못된 정보 하나), 고쳐도 그 이후
  흐름에 영향이 없는 경우

이 경우에는 어느 쪽을 재생성 대상으로 지정했는지와
그 이유를 한 줄로 남겨라. 그리고 만약 페이지를 재생성했으면
페이지 검수 단계부터 다시 하고, 다시 전체 검수를 돈다.
```
