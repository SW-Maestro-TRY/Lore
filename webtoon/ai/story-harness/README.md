# Lore 파이프라인 검증 하네스

두 파이프라인을 반복 실행하고, 결과를 사람이 블라인드로 판정하게 만드는 실험 장치다.

| | 스토리 (`story.py`) | 웹툰 (`webtoon.py`) |
| --- | --- | --- |
| 묻는 질문 | 이 이야기 재미있는가? | 그 이야기를 웹툰 형식으로 잘 옮겼는가? |
| 단계 | P1 카드 → P2 프리미스 → P3 구조검수 → SCENE | 4 큰줄거리 → **한 화씩** 5 설계 → 6 검사 → 7 컷 |
| 판정 | 사람이 장면을 읽고 "다음이 궁금한가" | 코드 게이트가 규칙 위반을 잡는다 |
| 화면 | `runs/read.html` (블라인드) | `runs/{run_id}/webtoon/webtoon.html` |
| 기준선 | `samples/` 카드 24장 + 바이블 2편 | — |

P1 은 **카드**를 만든다 — 플랫폼 목록에서 1초 안에 손가락을 멈추게 하는 한 장.
그 공식은 사람이 검수해 실제로 서비스에 나간 `samples/` 의 카드 24장에서 뽑았고,
`--card-mix` 는 새로 만든 카드를 그 24장 속에 섞어 사람이 골라낼 수 있는지 시험한다.

**순서를 지켜야 한다.** 웹툰 단계는 자동으로 이어지지 않는다. 사람이 블라인드 평가에서
"예"를 준 실행만 `webtoon.py` 로 넘어간다.

## 이 저장소가 어디까지 하는가

`C:\lore` 에는 하네스가 **셋** 있고, 이 저장소는 그중 하나다. 그림은 여기서 그리지 않는다.

```
캐릭터 JSON ─▶ story-harness ──────────────────▶ webtoon-harness ─▶ 완성 컷
              캐릭터 카드 · 이야기 엔진          영어 패널 프롬프트
              장면 · 컷 설계(한글)               레이아웃 · Gemini 그림 생성
              + 캐릭터 시트 이미지
                                    char-harness
                                    (레퍼런스를 어떻게 주면 같은 인물로
                                     보이는지 비교하는 별도 실험 도구)
```

| | 하는 일 | 산출물 |
| --- | --- | --- |
| **story-harness** (여기) | 캐릭터 → 스토리 → **컷 설계**. 컷 서술은 한글이고, 카메라(거리·앵글·전환)와 크기·여백·시선·리듬·칸 쓰기 같은 연출 메타를 붙인다 | `ep{MM}_cuts.json` |
| **webtoon-harness** | 그 컷 설계를 받아 **패널별 영어 프롬프트**를 만들고(`scenegen.py`), 레이아웃을 배정하고, Gemini 로 실제 그림을 뽑는다 | 이미지 · `viewer.html` |
| **char-harness** | 같은 인물이 컷마다 같게 나오는지 레퍼런스 조건(A~D)을 바꿔 가며 비교하는 실험 도구 | 비교 리포트 |

**작품 화풍(`--style`)은 이 저장소가 정하지 않는다.** `webtoon-harness/config.yaml` 의
`styles` 레지스트리에 있고, 현재 `webtoon` · `romance` · `flat` 셋이다
(기본값 `style_default: webtoon`). story-harness 는 그 문구를 **읽어 오기만** 한다 —
캐릭터 시트를 컷과 같은 그림체로 뽑아야 레퍼런스로 쓸모가 있기 때문이다.

**이 저장소에는 `--style` 이 없다.** `--charsheet` 는 저쪽 `style_default` 를
읽으므로, 시트를 뽑기 **전에** 그 값을 이번 화에 쓸 그림체로 맞춰야 한다.
컷은 `--style` 로 덮을 수 있지만 시트는 그럴 수 없다.

> ⚠️ `flat` 은 `render_style` 전환이 없다. `webtoon`·`romance` 는 normal/sd/emphasis
> 세 문구를 각각 갖지만 `flat` 은 문구가 하나뿐이라, `flat` 으로 뽑으면 SD 컷과 강조
> 컷이 정식 컷과 같은 그림체로 나온다. 이 저장소가 애써 배치한 그림체 리듬이 그림
> 단계에서 사라진다.

## 설치와 설정

```
pip install google-genai          # 기본 프로바이더
pip install openai anthropic      # 다른 프로바이더로 돌릴 때만
cp .env.example .env
```

`.env` 를 열어 키를 넣는다. **기본 프로바이더는 Gemini다.**
키는 https://aistudio.google.com/apikey 에서 발급한다.

```
PROVIDER=gemini
GEMINI_API_KEY=...
GEMINI_MODEL=gemini-2.5-flash
```

OpenAI 나 Anthropic 으로 바꾸려면 `.env` 의 `PROVIDER` 를 고치거나
`--provider openai` 를 붙인다.

우선순위는 **명령줄 인자 > 이미 설정된 환경변수 > `.env` > 코드 기본값** 이다.
`.env` 는 `.gitignore` 에 들어 있다.

| 항목 | .env | 명령줄 |
| --- | --- | --- |
| 프로바이더 | `PROVIDER=gemini\|openai\|anthropic` | `--provider openai` |
| 모델 | `GEMINI_MODEL` / `OPENAI_MODEL` / `ANTHROPIC_MODEL` | `--model gemini-2.5-pro` |
| 심사 모델 | `GEMINI_JUDGE_MODEL` / `OPENAI_JUDGE_MODEL` / `ANTHROPIC_JUDGE_MODEL` | `--judge-model` |
| 단계별 모델 | `MODEL_P3=` `MODEL_W6=` `MODEL_SCENE=` … | — |
| 온도 | `TEMP_CREATIVE=0.9` `TEMP_JUDGE=0.2` | — |
| 최대 토큰 | `MAX_TOKENS=8000` | `--max-tokens` |
| 토큰 단가 | `PRICES_FILE=prices.json` | — |
| 게이트웨이 | `GEMINI_BASE_URL` / `OPENAI_BASE_URL` (Azure 등) | — |

프로바이더를 바꿔도 파이프라인 규칙은 같다 — user 메시지 1개짜리 단발 호출, 히스토리
없음, JSON 응답, 온도 통제. 어느 프로바이더·모델로 돌았는지는 `meta.json` 의
`provider` / `model` / `stage_models` 에 남는다.

**심사 단계를 다른 모델로 돌리고 싶다면** `GEMINI_JUDGE_MODEL` 또는 `MODEL_P3` /
`MODEL_W6` 를 지정한다. 생성과 심사를 다른 모델이 맡으면 자기채점 편향을 한 겹 더
줄일 수 있다.

키가 비어 있으면 실행이 즉시 멈춘다. 키 없이 경로만 점검하려면 `--mock` 을 쓴다.

### 토큰과 비용

**호출 1건당 1줄**로 남는다. 합계만 남기면 "왜 이렇게 비쌌지" 에 답할 수 없다 —
한 실행 안에서도 단계마다 모델이 다를 수 있고(`MODEL_P3`, 심사 모델 분리), 재시도가
몇 번 돌았는지에 따라 비용이 배로 뛴다.

```jsonc
// runs/{run_id}/calls.jsonl · runs/{run_id}/webtoon/calls.jsonl
{"at":"…","stage":"P1","label":"…","model":"gpt-4.1","provider":"openai",
 "temperature":0.9,"seconds":12.3,"prompt_chars":12639,"stop_reason":"end_turn",
 "tokens":{"input":1200,"output":800,"cache_read":0,"cache_write":0,"total":2000},
 "cost_usd":{"input":0.0024,"output":0.0064,"cache_read":0.0,"cache_write":0.0,
             "total":0.0088}}
```

| 어디 | 무엇 |
| --- | --- |
| `calls.jsonl` | 호출별 단계·모델·토큰·비용. JSON 파싱 실패로 두 번 부르면 두 줄 — 재시도 비용이 사라지지 않는다 |
| `meta.json` 의 `usage` | 합계 + `by_model` (모델별 토큰) + `cost` (모델별 비용·합계·단가 기준일) |
| `summary.csv` | `total_tokens` · `cost_usd` · `cost_note` |
| `charsheet_meta.json` 의 `usage` | 실제로 그린 장수와 이미지 비용 |
| webtoon.html | [AI를 부른 기록] 표에 입력·출력·비용 |

**단가는 코드가 아니라 `prices.json` 에 있다** (100만 토큰당 USD). 요금은 코드와 다른
속도로 바뀌고, 모델을 바꿀 때마다 파이썬을 고치게 하면 결국 아무도 안 고친다.
새 모델을 쓰면 요금표를 직접 보고 한 줄 추가하고 `_as_of` 도 같이 고친다.

**모르는 단가는 0 으로 세지 않는다.** 0 은 "공짜"라는 뜻이라 거짓말이고, 합계를
조용히 낮춘다. 단가가 없는 모델은 그 호출의 `cost_usd` 가 `null` 이 되고, 이름이
`meta.json` 의 `unpriced_models` 에 남으며, 합계에는 `complete: false` 가 붙는다.
콘솔과 `summary.csv` 도 부분 합계라고 말한다:

```
-> ok · 42,000토큰 · $0.1408 (+단가 없음: some-unlisted-model) · 31초
```

날짜 고정본(`gpt-4.1-2025-04-14`)은 기본 이름의 단가를 따라간다. 접미사가 **날짜일
때만** 인정한다 — 그냥 앞자리로 맞추면 `gpt-4.1-mini` 가 `gpt-4.1` 단가를 물려받아
5배 비싸게 계산되고, 아무도 눈치채지 못한다.

## 0. 캐릭터 하나로 시작하기 (`--character`)

창작자가 실제로 쓰는 입구다. **캐릭터 → 스토리 → 웹툰.**

```
python story.py --character characters/example_minimal.json --with-charsheet
python story.py --charsheet --run-id {run_id} --pick    # 시트 채택
python webtoon.py --run {run_id}                        # 1화만 (기본)
python webtoon.py --run {run_id}                        # 다시 부르면 2화
cd ../webtoon-harness
python run.py --run-id {run_id} --episode 1 -c S        # 그림
```

**캐릭터 시트는 P3 통과 직후에 뽑는다.** `--with-charsheet` 를 붙이면 이야기가
끝나는 그 자리에서 이어서 뽑고, 안 붙이면 실행 끝에 순서를 안내한다.

P1 직후가 **아닌** 이유: P3 는 탈락 항목에 따라 P1 을 다시 뽑는다
(`target_stage == "P1"`). 거기서 시트를 뽑으면 방금 돈 주고 만든 시트가 버려진
카드의 것이 된다. P3 를 통과했다는 것은 외형 사양(`appearance_en` ·
`design_details` · `color_palette`)이 확정됐다는 뜻이고, 그 뒤로는 아무도 그것을
바꾸지 않는다.

컷을 다 뽑고 나서 시트를 만들면 순서가 거꾸로다 — 이미 그려진 컷과 시트가 다른
사람일 수 있다.

### 한 번에 한 화씩 만든다

**웹툰 단계는 기본으로 1화만 만든다.** 지금 보고 싶은 것은 1화이고, 1화가
재미있으면 그때 2화를 만든다. 다시 부르면 이어서 다음 화를 만든다.

예전에는 Arc 5개를 돌며 17화를 한꺼번에 설계했다. 1화를 보려고 17화를 다 만들어야
했고(호출 50여 회), 17화치 떡밥을 미리 스케줄링하느라 부채가 쌓여 마지막 Arc 가
무너졌다 — 실제로 Arc 3 에서 7개 → Arc 4 에서 11개(상한 5) → Arc 5 재시도 소진.

| | 예전 (Arc 일괄) | 지금 (한 화씩) |
| --- | --- | --- |
| 1화를 보기까지 | 17화 설계 · 50여 회 호출 | **3회 호출** |
| 비용 | ~$1.0 | **~$0.04** |
| 떡밥 | 17화치를 1화에서 스케줄링 | 화를 만든 뒤 **기록만** |

`--episodes N` 으로 여러 화를 한 번에 만들 수도 있지만, 기본은 1화다.

**같은 명령을 다시 치면 다음 화가 이어 붙는다.** 연재니까 그게 맞지만, 말해 주지
않으면 "1화만 만들었는데 왜 3화가 있지?" 가 된다 — 실제로 그 일이 있었다(10:44 ·
10:55 · 11:19 세 번 실행). 그래서 시작할 때 몇 화를 이어 만드는지 먼저 찍는다.

```
1화를 만듭니다 (한 번 더 부르면 다음 화가 이어집니다)
지금까지 2화가 있습니다 → 이번에 3화를 이어 만듭니다 (처음부터 다시 만들려면 webtoon/ 을 비우세요)
    -> ok · Arc 5 · 1화(누적 3화) · 컷 10(impact 2) · ...
```

요약 줄의 화 수는 **이번 실행에서 만든 것**이고, 괄호가 작품에 쌓인 총량이다
(`webtoon_summary.csv` 의 `episode_count` / `series_total`).

**Arc 는 작품에 한 번만 정한다.** 화를 하나씩 뽑는 구조라 `webtoon.py` 를 세 번
부르면 3화가 나오는데, 그때마다 4단계가 다시 돌면 3화는 1화가 따랐던 것과 **다른
Arc** 를 보고 설계된다 — `arcs.json` 은 마지막 것만 남아서 어긋난 줄도 모른다.
그래서 `arcs.json` 이 있으면 재사용하고, 방향을 다시 잡고 싶을 때만 `--replan` 을
붙인다. (이 가드가 없던 동안 실제로 W4 가 화마다 다시 돌아 같은 입력에 5,274 토큰씩
세 번 나갔다.)

### 3화가 1화를 잊지 않게 하는 것

한 화씩 만들면 생기는 위험이 하나 있다. 직전 화만 넘기면 1화에서 이름 붙인 인물이
3화에서 다른 이름이 되고, 1화에서 세운 설정이 3화에서 조용히 뒤집힌다. 요약을 이어
붙이는 것만으로는 부족하다 — 요약은 사건을 남기지 **사람과 규칙**을 남기지 않는다.

그래서 화를 만들 때마다 `webtoon/series.json` 에 **누적 명부**를 갱신하고, 다음 화를
쓰는 모델은 그 명부를 통째로 본다.

```jsonc
{
  "episodes_made": 4,
  "episodes": [ {"no": 1, "arc": 1, "title": "…", "summary": "…", "stinger": "…"}, … ],
  "cast": [ {"name": "이세윤", "first_episode": 1, "note": "재측정 신청자",
             "gender": "male",
             "appearance": "큰 키에 마른 체형, 짧고 헝클어진 검은 머리, 처진 눈매",
             "outfit": "회색 티셔츠에 연청 데님 자켓, 검은 슬랙스, 흰 스니커즈",
             "personality": "반 박자 늦게 반응하고 말할 때 눈을 못 맞춘다"} ],
  "facts": [ {"fact": "재측정은 5년에 한 번뿐이다", "first_episode": 1} ]
}
```

`cast` 와 `facts` 는 W5 가 그 화에서 **새로** 만든 것을 직접 신고한 값이다
(`new_cast` / `new_facts`). 모델이 무엇을 새로 만들었는지는 모델이 가장 잘 안다.

#### 조연 인물 카드 — 네 항목

`cast` 의 네 항목(`gender` / `appearance` / `outfit` / `personality`)은 **그림
단계를 위한 것**이다. 주인공에게는 캐릭터 시트가 있지만 조연에게는 없다. 여기
적힌 것이 그리는 쪽이 가진 전부이고, 비면 컷마다 다른 사람이 된다 — 실제로 같은
화 안에서 한 인물이 남자였다 여자였다 하고 옷이 매번 바뀌었다.

**`appearance` 와 `outfit` 을 나눈 이유**: 외형은 끝까지 안 바뀌지만 옷은 장면에
따라 바뀔 수 있다. 한 칸에 뭉치면 그리는 쪽이 둘을 구분하지 못해 옷을 바꾸려다
머리색까지 흔든다. 그래서 `outfit` 에는 **한 벌만** 적게 한다 — "보통 A나 B를
입는다" 라고 쓰면 컷마다 아무거나 고른다.

프롬프트로 시키기만 하면 모델이 빼먹으므로 **5단계 게이트가 검사한다.** 하나라도
비면 그 화를 되돌린다. 빼먹은 것은 그림 단계에 가서야, 이미 그린 뒤에 드러나기
때문이다.

명부는 다음 화 프롬프트에 `외형(고정)` / `옷차림(고정)` / `성격(고정)` 으로
되돌려 준다. 3화에서 머리색이나 옷이 바뀌면 독자에게는 다른 사람이다.

**엔진 카드의 「그 한 사람」(낙차의 예외)도 첫 등장 화에서 `new_cast` 에 적는다.**
이야기에서는 처음부터 있던 인물이라 "새로 등장"에 안 걸리는데, 그림 단계에는
주인공 시트밖에 없어서 그 사람도 낯선 사람이다 — 가장 자주 나오고 가장 많이
흔들리는데 검사를 빠져나가던 자리였다.

17화를 미리 설계하지 않는 대신, **지금까지 확정된 것은 하나도 잊지 않는 것**이
이 구조가 성립하는 조건이다.

### 떡밥은 사후 기록이다

질문 장부에서 **사전 계획을 걷어냈다.** 몇 화에 갚겠다는 계획(`planned_payoff_episode`),
연체 경고, Arc 상환 할당량이 전부 사라졌다. 연재는 앞 화를 보고 다음 화를 정하는
일이지, 17화치 상환 일정을 1화에서 짜는 일이 아니다.

지금 장부가 하는 일은 둘뿐이다: 화를 만든 뒤 **연 질문과 닫은 질문을 기록**하고,
다음 화를 쓸 때 **지금 열려 있는 질문 목록**을 보여주는 것. 열린 질문이 상한을
넘으면 "이번 화는 닫는 쪽에 무게를 두라"고 알려 주지만, 그건 경고이지 할당량이 아니다.

### 전체 흐름 — 어디까지가 이 저장소인가

| # | 단계 | 누가 | 무엇이 나오나 |
| --- | --- | --- | --- |
| 1 | 캐릭터 JSON 입력 (사진·이름·설정) | 사람 | `characters/*.json` |
| 2 | **LOOK** — 사진에서 외형·색·실마리 읽기 | story-harness | `look.json` (사진이 있을 때만) |
| 3 | **SEED** — 빠진 장르·세계관·한 줄 채우기 | story-harness | `seed.json` (빠진 게 있을 때만) |
| 4 | **P1** 캐릭터 카드 → **P2** 이야기 엔진 → **P3** 검수 → **SCENE** 도입부 | story-harness | `p1~p3.json` · `scenes.json` |
| 5 | **W4** 큰줄거리 → (한 화씩) **W5** 설계 → **W6** 검사 → **W7 컷** | story-harness | `ep{MM}_cuts.json` |
| 6 | 캐릭터 시트 이미지 (`--charsheet`) | story-harness → Gemini | `charsheet/*.png` |
| 7 | 컷 설계 → **영어 패널 프롬프트 + 레이아웃** | **webtoon-harness** | 프롬프트 · 레이아웃 |
| 8 | 프롬프트 + 화풍 → **실제 그림** | **webtoon-harness** → Gemini | 컷 이미지 · `viewer.html` |

**5번까지가 이 저장소다.** 컷 설계는 한글 서술 + 연출 메타(크기·여백·시선·beat·
render_style)이고, 그것을 영어 이미지 프롬프트로 옮기는 것은 7번 — webtoon-harness 의
`scenegen.py` 가 한다. 6번(캐릭터 시트)만 예외로 여기서 Gemini 를 부르는데, 시트는
컷을 그릴 때 레퍼런스로 쓰이므로 컷과 같은 그림체로 뽑아야 하기 때문이다.

4~5번 사이에 **사람의 블라인드 평가**가 들어간다(`--serve`). 재미없는 설계로 컷을
아무리 잘 뽑아도 재미없는 웹툰이 나온다.

캐릭터 1명 = JSON 파일 1개다. 빈 템플릿은 `characters/_TEMPLATE.json`,
채운 예시는 `example_minimal.json`(자유 서술만) · `example_full.json`(다 채운 것).

| 칸 | 필수 | 없으면 |
| --- | --- | --- |
| `photo` | — | 외형은 글에서만 나온다 |
| `character` (자유 서술) | — | 사진/필드에서 나온다 |
| `fields` (항목별) | — | 자유 서술에서 나온다 |
| `genre` | — | **AI 가 캐릭터를 보고 고른다** |
| `world` (프리셋 또는 직접) | — | **AI 가 캐릭터에 맞춰 만든다** |
| `story` | — | **AI 가 캐릭터에서 뽑는다** |

**필수는 하나뿐이다** — `photo` / `character` / `fields` / `name` 중 아무거나 하나.
사진 한 장만 넣어도 웹툰까지 간다.

### 빈 칸을 누가 채웠는지 남는다

```
LOOK  사진 → 머리·눈·체형·복장·색(hex)·이야기 실마리     (사진이 있을 때만)
SEED  빠진 장르·세계관·한 줄을 채움                      (빠진 게 있을 때만)
  ↓
P1 카드 → P2 엔진 → P3 판정 → SCENE → W4~W7 컷 → 웹툰
```

두 단계 모두 **줄 것이 있을 때만** 돈다. 사진이 없으면 LOOK 을 부르지 않고,
장르·세계관·한 줄이 다 차 있으면 SEED 를 부르지 않는다 — 안 부르면 돈이 안 나간다.

**작가가 적은 것은 AI 가 바꾸지 않는다.** 빈 칸만 채우고, 무엇을 채웠는지
`runs/{run_id}/seed.json` 의 `filled` 와 `meta.json` 의 `ai_filled` 에 남긴다.
프롬프트로만 막으면 언젠가 덮어쓰므로 코드에서 한 번 더 막는다 —
값이 이미 있으면 모델 응답을 무시한다.

사진에서 읽은 외형은 캐릭터 재료의 **맨 앞**에 붙는다. 뒤에 오는 자유 서술보다
세다 — 하나는 보인 것이고 하나는 적힌 것이다. 사진에 안 보이는 칸은 비워 두고
(`not_visible`), 그 자리는 뒷단계가 정한다. 안 보이는 하의를 지어내면 그 바지가
100컷 내내 따라다닌다.

### 장르·스토리 템플릿 주입

**현재 준비된 것** (둘 다 이미 파이프라인에 연결돼 있다):

| 파일 | 들어 있는 것 | 주입되는 곳 |
| --- | --- | --- |
| `samples/genre_template.json` | 로맨스 · 판타지 · 액션 · 스릴러 · 일상 · 개그 **6종**. 각 장르마다 분위기/소재/캐릭터 관계/사건 전개 패턴 + 사례분석 + 체크리스트 | P2 |
| `samples/story_templates.json` | 스토리 구조(3막·영웅의 여정) · 반전과 플롯 장치(복선·클리프행어) · 에피소드와 시즌 구성 · 웹툰 스토리텔링 팁 **4절** | P2 (앞 2절) |

아직 없는 것: 코미디는 `개그` 로 있지만 SF·무협·사회파 미스터리 등은 없다.
`hunter`·`idol`·`academy` 는 자기 항목이 없어 아래 매핑으로 빌려 쓴다.

캐릭터의 `genre` 를 보고 **걸리는 템플릿만** 골라 P2(엔진 설계)에 넣는다.
매핑은 `samples/genre_template.json` 의 `_preset_map` 에 있다.

```
hunter  → 판타지 + 액션 + 스릴러      romance → 로맨스
academy → 판타지 + 일상               idol    → 일상 + 로맨스
```

두 어휘를 하나로 합치지 않은 이유: 프리셋 키(`hunter`)는 **소재** 축이고 장르명
(`판타지`)은 **전개 문법** 축이라 다른 것을 잰다. 한쪽을 버리면 "헌터물의 무대에
스릴러의 전개를 얹는다" 같은 선택지가 사라진다.

한글 장르명(`판타지`)은 그대로 쓰고, 자유 입력(`"로맨스 판타지"`)은 문자열 안에서
장르명을 찾는다. **못 찾으면 아무것도 주입하지 않는다** — 안 맞는 장르 문법은 안
주는 것보다 나쁘다. 모델이 캐릭터가 아니라 그 문법을 따라가기 때문이다.

전부 보내면 16,793자다. 골라 보내면 **4,129자(25%)** 다.

무엇을 썼는지는 `meta.json` 의 `templates_used` 에 남는다 — 결과를 보고 템플릿을
고칠 때 어디를 고칠지 알아야 한다.

### 기존 작품이 결과물에 들어가지 않게 하는 것

템플릿에는 실제 웹툰·드라마 제목과 줄거리가 26편 실려 있다. 그건 사람이 장르를
이해하라고 있는 것이지 **모델에게 줄 재료가 아니다.** 세 겹으로 막는다.

| 겹 | 무엇 | 왜 |
| --- | --- | --- |
| 1. 칸 선별 | `대표작` · `참고자료` · `examples` · `visual` 은 프롬프트에 도달하지 않는다 (`TEMPLATE_DROP_FIELDS`). 보낼 칸은 허용 목록으로 정한다 | 특정 작품의 제목·줄거리·URL |
| 2. 본문 삭제 | 남은 설명문 **본문**에 박힌 작품명을 `(작품명 생략)` 으로 치환한다 (`redact_titles`) | 칸 선별은 칸 단위라 문장 속까지 못 본다 |
| 3. 결과 검사 | 생성된 P2 에 작품 제목이 있으면 게이트가 잡아 재생성시킨다 (`check_borrowed_titles`) | 모델은 자기가 원래 아는 작품도 꺼낸다 |

2번은 1번만으로 부족해서 생겼다. `story_templates.json` 의 설명문에는
`『조명가게』에서는 …` `『왕좌의 게임』 S1E9 에서는 …` 처럼 작품명이 문장 안에
들어 있어서, 칸을 골라내도 그대로 따라온다. 지워도 배울 것은 남는다 — 필요한 것은
"어느 작품이 그랬다"가 아니라 "그 자리에서 무엇을 했다"이기 때문이다.

3번이 1·2번과 겹쳐 보이지만 대신하지 못한다. 프롬프트를 막아도 모델의 학습된
지식은 막지 못한다.

장르 관습(각성·게이트·회귀)은 누구의 것도 아니므로 자유롭게 쓴다. 특정 작품이
만든 고유한 설정과 이름만 쓰지 않는다.

### 세계관

`worlds.json` 의 프리셋을 키로 고르거나(`{"preset": "hunter_gate"}`), 직접 쓰거나
(`{"text": "..."}`), 둘 다 비우고 AI 에게 맡긴다. 직접 쓴 것이 프리셋을 이긴다.

프리셋이든 직접 쓰든 세 가지만 있으면 된다: **(1) 어디이고 언제인가 ·
(2) 이 세계의 규칙 하나 · (3) 그 규칙이 이 캐릭터에게 불리하게 걸리는 지점.**
(3)이 없으면 세계관이 아니라 배경 설명이다.

## 1. 스토리 파이프라인 (배치 실험용)

```
python story.py --input inputs.csv --n 3          # 파이프라인만 (한 줄 입력 → 카드)
python story.py --input-card cards.json          # StoryCard JSON 입력
python story.py --input inputs.csv --n 3 --control  # 대조군만
python story.py --input inputs.csv --n 3 --both     # 둘 다 (실험용 권장)
```

여러 입력을 한 번에 돌려 비교하는 경로다. 창작자 한 명이 자기 캐릭터로 시작할
때는 위의 `--character` 를 쓴다.

`inputs.csv` 는 `character, one_line, genre` 열을 가진다.
`--n` 은 같은 입력을 몇 번 반복할지 — 재현성(문서 8장 성공기준 3번) 확인용이다.

### 흐름

```
P1 ──→ P2 ──→ [코드 게이트] ──→ P3 ──→ SCENE ──→ [장면 점검 11항목] ──→ scenes.md
        ↑          │                  │                    │
        └──────────┘ 실패 시           └─ no 있으면          └─ 걸리면 지시를 넣어
           P3 호출 없이 재생성            target_stage 재실행     SCENE 재생성
                                          (최대 2회)            (기본 1회)
```

**P3 는 항상 새 API 호출이다.** 실제로 이 하네스는 어떤 단계에서도 대화 히스토리를
쌓지 않는다 — 매 호출이 user 메시지 1개짜리 독립 호출이다. P3 프롬프트에는
`{character_sheet}` 와 `{premise_json}` 만 들어가며, 원본 입력(작가가 준 한 줄, 인물)과
재생성 지시는 코드가 차단한다(`P3_FORBIDDEN_VARS`). 자기가 만든 걸 자기가 채점하면
무조건 통과가 나오기 때문이다.

온도는 P1/P2/SCENE/CONTROL 0.9, P3 0.2. 출력은 전부 JSON이고, 파싱 실패 시 1회만
재요청한 뒤 또 실패하면 실패 처리한다.

### P1 — 상업 훅 공식

P1 이 만드는 것은 캐릭터 시트가 아니라 **카드**다. 이 카드는 플랫폼 목록에서 다른 카드
수십 장과 나란히 놓이고, 독자는 한 장에 1초를 쓴다. 공식은 `samples/` 의 검수 통과
카드 24장(장르 4종 × 6장)과 스토리 바이블 2편에서 뽑았다.

```
samples/romance.ts  idol.ts  hunter.ts  academy.ts    카드 24장 (정통 3 + 반전 3)
        로판.txt  좀비아포칼립스.txt                   완성 기획서 2편
```

카드 24장은 장르마다 **정통 3장 + 반전 3장**이다. 원본 주석의 표현대로,
"반전 카드가 뽑히는 게 이 세계관의 진짜 훅이다 — 절대 정통 카드로만 채우지 말 것."

프롬프트에는 같은 장르 샘플 6장이 통째로 들어간다. 장르는 `samples.guess_genre()` 가
입력 문자열에서 고르고, 못 고르면 전 장르의 대표 카드를 보여준다.

| 필드 | 공식 | 코드가 보는 것 |
| --- | --- | --- |
| `intro` | [평범한 기대] + 전환어 + [이례] | **전환어**("그런데/하필/알고 보니/눈 떠보니/~인 줄 알았는데")가 없으면 반려. 70자 초과 반려 |
| `rank` + `rank_irony` | 직함 (괄호 안 아이러니·카운트다운) | 괄호 내용이 비었거나 `rank` 안에 없으면 반려 |
| `relational_gap` | 모두에게 X / 단 한 사람에게만 Y | 네 칸(`to_everyone`/`to_one_only`/`anchor`/`exception_reason`) 필수. anchor 가 "그 사람" 수준이면 반려, exception_reason 이 "운명이라서"면 반려 |
| `wish_fulfillment` | 독자가 대리 체험하는 것 | 비어 있으면 반려 |
| `appearance` | hair/eyes/impression/element 네 칸 | 빈 칸 반려 |
| `appearance_en` | 영문 한 문단 | 한글 혼입 반려. hair/eyes/build/clothing 다 있어야 한다 |
| `visual_hook` | 첫 컷에서 멈추는 이유 | 평가어("잘생김·매력적"…) 반려. 신체·복장·형태를 하나는 지목해야 한다 |
| `visual_gap` | 외형 첫인상을 B가 배신 | **`b_trait_word` 를 그대로 포함**해야 한다 |
| `fate_beats` | ①상황 ②사건 ③위협 ④비대칭 카드 | 정확히 4개. ④가 각오·다짐이면 반려 (P3 가 "뒤집히는가"를 따로 판정) |
| `quote` | 인정 → 전환 → 여운 3단 | 2~3문장. 너무 짧으면 반려 |

기존 저격 구조(`ea_key_word` / `b_trait_word` / 공존 강제 / want·need)는 그대로다.
공식은 그 위에 얹힌 것이지 대체한 것이 아니다.

**`relational_gap` 이 이 공식에서 가장 오래 가는 장치다.** 캐릭터 혼자면 낙차가 한 번
보이고 끝나지만, 예외가 되는 사람이 있으면 그 둘이 나올 때마다 재발동한다
(로판 바이블: "모두에게는 미친개, 엘리아나에게만은 대형견"). 1인 완결형도 허용하되
`solo: true` + `solo_reason` 을 요구하고, P3 는 그 항목을 `skip` 으로 기록한다.

`appearance_en` 은 웹툰 하네스 `config.yaml` 의 `character_appearance` 로 직결된다.
지금까지 사람이 손으로 채우던 값이라 그림과 이야기가 아무 데서도 묶이지 않았다.

### 카드 입력

```
python story.py --input-card cards.json              # StoryCard JSON 을 P1 이 확장
python story.py --input-card cards.json --genre romance
python story.py --input inputs.csv                   # 한 줄 입력 → P1 이 카드로 승격
```

장르는 카드의 `genre` → id 접두어(`romance-01`) → `--genre` 순으로 찾는다.
셋 다 없으면 멈춘다 — 장르를 모르면 어느 샘플을 보여줄지 고를 수 없다.

### P2 직후 코드 게이트

P3 를 호출하기 **전에** 코드만으로 판정한다. 실패하면 P3 호출 없이 P2 를 다시 뽑는다.

- 사건 목록: `generative_check` 10개 이상, `source` 별 rule/cost/irony 각 3개 이상
  (구판 `causal_chains` 가 들어오면 3개 / 각 1개 기준으로 자동 전환된다)
- `connector` 에 "그리고 나서" 류 단순 나열 접속사 없음 (`prompts/banned_connectors.txt`)
- `forbidden_subversion` 이 비어있지 않음

### 장르 배신 — 트로프는 약속, 하위 기대는 배신

P2 의 장르 배신 지시가 바뀌었다. 장르 자체를 배신하면 안 된다 — 독자는 그 장르를
**원해서** 들어왔다. 빙의물을 고른 사람은 빙의를 보고 싶어 한다. 그걸 안 주면 배신이
아니라 사기다. 그래서 두 층으로 나눈다.

- `genre_promise` — 지킬 것. 빙의는 일어나고, 각성은 일어나고, 데뷔는 다가온다.
- `subversion_axis` — 뒤집을 축 하나. 섞으면 아무것도 안 남는다.
- `genre_betrayal` — 그 축으로 하위 기대를 뒤집는 방식.

반전 축 6종은 샘플 카드의 반전분(04~06)에서 실제로 쓰인 것들이다.

| 축 | 샘플 |
| --- | --- |
| 성별 | 여주인공에 빙의한 줄 알았는데, 후궁만 서른일곱인 바람둥이 황태'자' |
| 종족 | 빙의는 성공했는데, 하필 악역 영애가 키우는 고양이 |
| 위상 | 이름도 안 나오는 하녀 A로 빙의, 알고 보니 원작 최종 흑막 |
| 능력 | 능력이 '유통기한 되돌리기'인 S급 폐기물 처리반 |
| 정체 | 각성 판정 결과가 '인간 아님'. 던전 몬스터로 등록된 당신 |
| 관계 | S급 헌터로 각성한 줄 알았더니, 최강 길드마스터의 회귀 전 남편 |

코드 게이트가 `genre_promise` 존재와 `subversion_axis` 가 6종 중 하나인지를 본다
(`normalize_axis` 가 "gender"/"신분" 같은 표기도 받아준다).

`fate_beats` 는 엔진 카드에 실려 4~7단계 전부로 넘어가고, W7 은 **1화일 때 이 4개를
오프닝 시퀀스로 배치한다**(w7.txt 2.5항). 카드를 뒤집은 독자가 처음 읽는 문장이
그대로 1화의 첫 컷들이 된다.

### P3 판정 (코드가 계산)

| 조건 | 판정 | 다음 |
| --- | --- | --- |
| 체크에 no 1개 이상 | 별로 | `regeneration_directive` 를 `target_stage` 에 주입해 재실행 (최대 2회) |
| 전부 yes + capture=yes + first_question 있음 + 클리셰 없음 | 맛있음 | SCENE 진행 |
| 전부 yes 지만 capture=no 또는 클리셰 감지 | 보통 | 사람 확인 필요 (중단) |

재생성 2회를 소진하면 `사람확인필요` 로 표시하고 중단한다.
모델이 `null` 대신 `"null"`·`"없음"` 을 뱉는 경우는 코드가 정규화한다.

체크는 9개다. 기존 6개(①~⑥)에 카드 공식 3개가 붙었다.

| 체크 | 묻는 것 |
| --- | --- |
| ⑦ `intro_hook` | intro 가 공식 구조이며, **시장 기준선 옆에서 눌리지 않는가.** 프롬프트에 같은 장르 샘플 intro 6줄이 들어가고, 판정에는 그중 가장 비슷한 것을 인용한 비교가 **반드시** 있어야 한다. 비교 없는 "좋다/나쁘다"는 무효 |
| ⑧ `relational_gap_exists` | 낙차가 실재하고 `exception_reason` 이 구체적인가. `solo: true` 면 `skip` (통과도 탈락도 아니고 `p3_skipped_items` 에 기록) |
| ⑨ `fate_beats_turn` | ④가 ③의 위협에 대해 나만 가진 것이고, 앞 셋에서 예측되지 않는가. 근거에 ③과 ④를 **둘 다** 인용해야 뒤집혔는지 보인다 |

⑦⑧⑨ 는 캐릭터 시트의 결함이므로 `target_stage` 는 P1 이다.

### 어디를 보면 되나 — 게이트와 프롬프트의 경계

**원칙: 숫자로 셀 수 있는 것은 코드가 세고, 프롬프트는 목적만 말한다.**
같은 규칙을 양쪽에 쓰면 프롬프트가 길어지고, 모델이 세는 데 주의를 쓰느라
정작 판단해야 할 것을 놓친다. 실제로 7단계 자기검사는 38항목 중 24개가
게이트와 같은 말이었다.

| 무엇 | 어디 |
| --- | --- |
| 7단계가 지켜야 할 수치 (얼굴·앵글·전환·말 밀도·sd·bleed) | `webtoon.py:110-230` 상수 정의부 — 한 줄마다 왜 그 숫자인지 실측이 적혀 있다 |
| 그 수치를 실제로 막는 곳 | `gate_cuts` · `gate_text` · `gate_camera` · `gate_layout` (`webtoon.py:1307~`) |
| 되돌리진 않고 경고만 하는 것 | `prose_warnings` (`webtoon.py:1756~`) — 카메라 낱말, 명부에 없는 화자, 혼잣말 |
| 모델이 스스로 봐야 하는 것 (게이트 없음) | `prompts/w7.txt:560` 자기검사 16항목 |
| 무대 (장소·시간대·날씨·광원·사물·동선) | `prompts/w5.txt:59` 정의 · `gate_setting` (`webtoon.py:1183`) 이 강제 |
| 상태 카드 (이 화가 남긴 자국) | `prompts/w5.txt:109` · `SeriesState.status` (`webtoon.py:731`) · `runs/{id}/webtoon/series.json` |
| 조연 명부 | `p1.json` 의 `supporting_cast` → `series.json` 의 `cast` → 엔진 카드 `[조연]` |
| 그림 단계에 넘기는 무대 | `webtoon-harness/prompts/scene_gen.txt:21` `[STAGING]` |

산출물로 직접 보기:

```
python webtoon.py --stats --run RUN_ID     # 화별 컷 지표 한 표 + 어느 프롬프트로 뽑았는지
runs/{id}/webtoon/engine_card.txt          # 화마다 다시 만들어진다. [조연]·[지금 남아 있는 것]
runs/{id}/webtoon/series.json              # 연재 명부 — cast / status / facts / places / zones
runs/{id}/webtoon/webtoon.md               # 화별 컷 표 + 거리·앵글·전환 분포
runs/{id}/webtoon/webtoon.html             # 같은 것을 브라우저에서
```

`--stats` 는 화끼리 세로로 비교한다. 프롬프트를 고친 뒤 앞 화보다 나빠졌는지
보는 자리다 — 맨 오른쪽 열이 그 화를 뽑은 w7 프롬프트 해시다.

### 장면 점검 11항목 (코드 판정, API 호출 없음)

문서 6장. 걸린 항목은 그대로 수정 지시로 조립되어 `{fix_directive}` 에 들어간다.

**1~8 — 하지 말아야 할 것**

1 선택에서 시작 · 2 설정 증발 · 3 라벨 서술 · 4 장면 반복 · 5 대사 없음 ·
6 1회성 신규요소 · 7 **소품 구동** · 8 출처 단일

7번이 핵심이다. 금지어 목록이 아니라 `"X를 발견했다 / X가 놓여 있었다"` 문형 하나만
보고, 설정에 있는 것이거나 여러 장면에서 쓰이면 통과시킨다.

**9~11 — 해야 할 것**

1~8 이 전부 금지 항목이라, 다 지켜도 **아무 일도 안 일어나는 장면이 통과한다.**
실제로 8개를 통과한 원고가 세 장면 내내 같은 사람을 밀어내기만 하고 끝났다.
프롬프트 맨 위의 세 가지 목표를 코드도 본다.

| 항목 | 걸리는 조건 | 왜 |
| --- | --- | --- |
| 9 회피로 시작 | 첫 장면 `choice` 가 피한다·거리를 둔다·웃어넘긴다 류 | 회피는 선택처럼 보이지만 판을 그대로 둔다. 부정형(`피하지 않는다`)과 다른 뜻(`피해를 감수한다`)은 걸리지 않는다. **거절·숨김·거짓말·선 긋기는 회피가 아니다** — 상대에게 무언가를 하는 행동이다 |
| 10 훅의 주어 | `hook` 이 조연 이름으로 시작하거나 주인공이 아예 없음 | 독자는 주인공을 따라 읽는다. 성을 뗀 이름(`민시하`→`시하`)도 같은 사람으로 본다 |
| 11 인식만 바뀜 | 모든 장면의 `changed` 가 "알게 된다 / 눈치챈다 / 느낀다" 류 | 되돌릴 수 없게 된 일이 하나도 없다는 뜻. 한 장면이라도 실제로 벌어지면 통과 |

재생성 상한은 `--scene-fix` (기본 **2**). 항목이 11개로 늘어 한 번에 다 맞추기
어렵고, SCENE 은 호출 1회에 약 5센트라 한 번 더 주는 편이 싸다.

### 조연 명부 — 인물은 P1 에서 끝나지 않는다

같은 캐릭터 파일을 두 번 돌렸더니 후배 이름이 `하윤재` → `장지운` 으로 바뀌었고,
그림에서는 설정상 남자인 후배가 여자로 그려졌다. **조연은 캐릭터 시트가 없다** —
명부에 적힌 것이 뒷단계가 가진 전부다.

명부는 한 번 정하고 끝나는 게 아니라 **연재하면서 자란다.**

```
p1.supporting_cast        이야기 시작 시점에 있는 사람 (게이트가 강제)
        │                 anchor = 로맨스면 상대역. 반드시 포함
        ↓
   series.json  ←──────── 5단계 new_cast (화마다 새로 나온 사람)
   (0화 = 스토리 단계 확정, N화 = 그 화에서 등장)
        │
        ↓ 화마다 다시 만든다
   엔진 카드 [조연]  ──→ 5·6·7단계
        │
        └──→ webtoon-harness/supporting.py ──→ 컷 프롬프트
                                              성별은 영어로 (남성 → male)
```

**엔진 카드는 화마다 다시 만든다.** 예전에는 시작할 때 한 번 만들고 그대로 썼다.
5단계는 `series_state` 로 명부를 따로 받지만 6·7단계는 카드가 전부라, 3화에서 나온
인물이 7화 컷 설계에서 사라졌다 — 그리는 쪽이 그 사람을 처음 보게 된다.

| 단계 | 인물에 대해 하는 일 |
| --- | --- |
| P1 | 시작 시점 인물을 **정한다**. `gate_supporting_cast` 가 성별·외형·anchor 포함을 강제 |
| SCENE | 명부에 있는 사람만 **쓴다**. 여기서 만든 이름이 엔진 카드로 새는 것을 막을 뿐, 인물을 정하는 자리가 아니다 |
| W4 (Arc) | 큰 줄기. 인물을 늘리지 않는다 |
| **W5 (화)** | 이야기가 실제로 자라는 곳. `new_cast` 로 사람을 **추가한다** (성별·외형·옷차림·성격 필수, 게이트가 검사) |
| W7 (컷) | 카드의 조연 + 이 화의 `new_cast` 만 그린다. 처음 나오는 컷에 성별·외형을 옮겨 적는다 |

`relational_gap.solo: true` 면 조연이 없는 것이 맞는 답이므로 게이트를 걸지 않는다.
이미 명부에 있는 사람은 `new_cast` 에 다시 적지 않아도 되고, 대사 경고도 붙지 않는다.

### 블라인드 평가

```
python story.py --serve          # http://127.0.0.1:8765/
```

`read.html` 은 **`scenes.md` 본문만** 보여준다. JSON·체크리스트·조건(pipeline/control)은
전혀 표시하지 않는다. 각 항목 아래에 "다음 장면이 궁금한가? [예][아니오]" 와 한 줄 메모
입력칸이 있고, pipeline 과 control 이 무작위로 섞여 배치된다. run_id 와 조건은 화면에

파일을 그냥 `file://` 로 열어 평가했다면:

```
python story.py --resolve-blind blind_raw.csv
```

### 카드 믹싱 — 골라낼 수 있는가

```
python story.py --card-mix --genre romance --n 3      # 시험지 생성
python story.py --card-mix-score "2,5,9"             # 뷰어가 고른 번호로 채점
```

새 P1 으로 카드 3장을 뽑아, 같은 장르 **샘플 카드 6장과 섞어** 9장을 무작위 순서로
보여준다. 사람이 하는 일은 하나다 — **AI 가 만든 3장을 골라내기.**

묻는 것이 "이 카드가 좋은가"가 아니라는 점이 요점이다. 좋다/나쁘다는 기준이 사람마다
다르지만, 골라낼 수 있는지에는 정답이 있다. 못 고르면 그 카드는 이미 서비스에 나가 있는
것들과 같은 급이다.

| 맞힌 수 | 판정 |
| --- | --- |
| 0~1장 | **합격** — 우연히 찍은 것과 같다 (9장 중 3장을 찍으면 기대 적중은 1장) |
| 2장 | 애매 |
| 3장 | **불합격** — 티가 났다 |

- 정답은 `mix_key.json` 에만 있고 **HTML 소스에는 없다.** 페이지를 열어 봐도 안 나온다.
- 결과는 `runs/mix_result.csv` 에 누적된다 (맞힌 수, 헛짚은 수, 우연 기대치, 판정).
- 시험지는 두 출처의 카드를 **같은 렌더러**로 그린다. 필드 이름이나 칸 수가 다르면
  사람은 내용이 아니라 형식을 보고 골라내는데, 그건 이 시험이 재려던 것이 아니다.
  같은 이유로 코드가 번호(`①`)와 구분 기호(`/`)를 지운다 — 실제로 첫 실행에서 그
  두 가지가 그대로 나왔고, 지우지 않았으면 서식만 보고 3장을 다 골라낼 수 있었다.
- 한 묶음 안의 카드들은 서로 닮지 않게 만든다. 같은 프롬프트를 3번 부르면 활동명이
  셋 다 같은 단어로 나오고, 그러면 사람은 "비슷한 세 장"을 통째로 짚는다.
  그래서 뒤 카드에는 앞서 만든 카드 목록이 "겹치지 말 것"으로 들어간다.

## 2. 웹툰 파이프라인

```
python webtoon.py --list                      # 웹툰으로 만들 수 있는 실행 목록
python webtoon.py --run <run_id>              # 그 실행을 웹툰으로  (= [웹툰으로 만들기])
python webtoon.py --all-passed                # 사람이 '예' 준 실행 전부
python webtoon.py --run <run_id> --resume     # 중단 지점부터 이어서
python webtoon.py --run <run_id> --episodes 3 # 한 번에 3화까지
python webtoon.py --run <run_id> --replan      # Arc(큰 줄거리)를 다시 잡는다
python webtoon.py --run <run_id> --cuts-only  # 회차는 그대로, 컷만 다시 뽑기
python webtoon.py --run <run_id> --mock       # API 없이 게이트·장부만 점검
python webtoon.py --check                     # 프롬프트 변수 계약만 점검 (0원)
```

`--max-retries` (기본 2) 는 4·5단계에서는 **실행 전체**의 상한이고, 7단계에서는
**화마다**의 상한이다. 아래 "7단계 재시도 예산은 화마다" 참조.

사람 판정이 "예"가 아니면 실행을 거부한다. 재미없는 설계로 컷을 아무리 잘 뽑아도
재미없는 웹툰이 나오기 때문이다. 검증 목적으로 건너뛰려면 `--skip-human-gate`.

### 접점 — 작품 카드(엔진 카드)

코드가 조립하며 4~7단계 **모든 프롬프트에 원문 그대로** 삽입된다.
로그라인 · 장르기대/배신 · RULE · COST · IRONY · 낙차 · 엔진급 질문 · 금지된 뒤집기 ·
주인공(want/need/겉/속) · **작가가 처음 준 한 줄(원문)** · **사람이 통과시킨 1화 도입부
(한 줄 압축 + 그 장면의 선택)**.

마지막 두 블록이 핵심이다. 이게 빠지면 회차·컷 단계가 빈칸을 학습 데이터 평균값
(의문의 책·빛나는 유물)으로 채운다.

### 게이트

| 단계 | 함수 | 코드가 판정하는 것 |
| --- | --- | --- |
| 4 | `gate_arcs` | Arc 4~6개 · order 1부터 연속 · 화 수 2~5 · rule/cost/irony 각 1회 이상 주 동력 · 반전 비율 ≥ 1/3 |
| 5 | `gate_episodes_shape` | 화 수가 Arc 계획과 일치 · title/summary 있음 · engine_fired 비어있지 않음 · stinger.text 있음 · new_cast 의 성별/외형/옷차림/성격 · **Arc 단위** 상환 1회 이상 |
| 5 (무대) | `gate_setting` | place · time · movement 있음 · props 2개 이상 |
| 6 | `summarize_review` | 화별 pass 계산 · 장부 반영 · 재생성 라우팅 · **eq 위반 시 즉시 중단** |
| 7 (장면) | `gate_scenes` | 장면 2~5개 · 장면마다 what·mood 있음 · 장면당 2~5컷 · last_cut 오름차순이고 마지막이 마지막 컷 |
| 7 (내용) | `gate_cuts` | 컷 8~16 · cut_number 연속 · 엔진 컷 실재 및 마지막 1/4 몰림 금지 · 스팅어가 마지막 컷 · dramatic_irony 있으면 독자우위 컷 최소 1개 |
| 7 (연출) | `gate_layout` | 값이 목록에 있는가(6필드) · turn 최소 1개 · impact 2개까지 · 같은 beat/size 4연속 금지 · 마지막 컷 size 는 impact/tall, beat 는 turn/hold · sd 5개까지·beat 제한·스팅어 금지 · bleed 1개·turn/release 만 · breakout 2개·build/turn/release 만 · sfx 한글 8자 이내 |
| 7 (카메라) | `gate_camera` | 얼굴 거리 55% 이하 · 같은 shot 4연속 금지 · 수평 앵글 70% 이하 · 기울임 2개까지 · 첫 컷 transition 은 `장면` · 같은 transition 4연속 금지 · transition 3종 이상 |
| 7 (말) | `gate_text` | 말 있는 컷 50% 이상 · 말 없는 컷 2연속까지 · 첫 컷에 말 · `장면` 전환 컷에 말 |
| 7 (대사) | `gate_dialogue` | 대사가 있으면 `speaker` 가 있어야 한다 (이것 하나뿐) |

되돌리지 않고 **경고만** 하는 것은 `prose_warnings` 에 있다. 시간 경과·속마음 서술 ·
서술에 남은 카메라 낱말 · 인물이 들어간 인서트 · 인서트/원경/`분위기` 전환 0개 ·
대사가 한 줄씩 고립 · 혼잣말이 전부 말풍선 · 명부에 없는 화자 · 침묵 컷 2개 미만 ·
SD 컷에 sfx 없음 · narration 이 서술과 겹침. 무엇을 게이트에 넣고 무엇을 경고로
남길지는 아래 "게이트에 넣을 것과 경고로 남길 것" 에 기준을 적었다.

### 장면이 먼저다 — 컷은 그 답이다

컷 필드를 늘리다 보면 카메라를 정교하게 잡는 쪽으로만 힘이 실린다. 그런데 콘티를
사람이 볼 때 처음 묻는 것은 **"이게 무슨 장면이냐"** 이고, 컷은 그 답을 어떻게
보여줄지일 뿐이다. 예전 작업 순서는 컷 수부터 정하고 beat 수열로 넘어가서 장면의
의도를 **한 번도 묻지 않았다.**

그래서 7단계가 컷보다 먼저 `scenes` 를 낸다.

| 칸 | 무엇 |
| --- | --- |
| `what` | 무슨 장면인가. 누가 어디서 무엇을 하는 장면인지 한 줄 |
| `mood` | 어떤 공기여야 하는가 — **컷의 빛·거리·여백이 여기서 나온다** |
| `last_cut` | 이 장면이 끝나는 컷 번호 (한 장면 2~5컷, 한 화 2~5장면) |

`what` 과 `mood` 는 라벨이면 실패다. "도입부" · "긴장감 있게" 는 아무것도 정하지
않은 것이다. `gate_scenes` 가 빈 칸과 컷 배분을 검사하고, "라벨인가" 는 코드가 볼 수
없으므로 프롬프트의 자기검사에 남겼다.

**장면 경계가 모델 몫으로 넘어왔다.** 예전에는 `derive_layout` 이 beat 만 보고
"hold·turn 자리 중 2~5컷" 으로 끊었는데, 어디서 끊을지는 산수가 아니라 "여기까지가
한 장면" 이라는 판단이고 그 판단에는 what·mood 가 딸려 온다. 이제 `scene_break` 는
`last_cut` 을 옮겨 적는다. `scenes` 가 없거나 깨져 있으면 예전 계산으로 되돌아간다 —
옛 run 을 그대로 다시 그릴 수 있어야 하기 때문이다.

`webtoon.md` · `webtoon.html` 은 컷 표 **위에** 장면을 먼저 보여준다.

```
**장면**

1. (컷 1~4) 라운지에서 시하가 후배들과 있는데 윤재가 또 옆자리에 앉는다
   분위기 · 느긋한 오후. 아직 아무 문제 없어 보이는데, 시하만 조금씩 자세를 고쳐 앉는다
2. (컷 5~9) ...
```

### Arc 소화보다 이 화의 재미가 앞선다

`w5.txt` 와 `w7.txt` 에 같은 말을 박아 두었다 — **Arc 를 얼마나 진도 뺐는지는 아무도
안 본다.** 독자가 보는 것은 이 한 화뿐이고, 이 화가 재미없으면 다음 화는 없다.
둘이 부딪히면 이 화를 택한다. Arc 는 다음 화가 다시 읽는다.

### 나레이션이 한 가지 일만 하고 있었다

컷 텍스트 네 칸 중 나레이션이 사실상 죽어 있었다. 실측(오늘 run, 37컷):
대사 54% · **나레이션 13%** · 속마음 8%. 그리고 그 나레이션 셋이 전부 같은 일을 했다.

```
[1]  늦은 오후, 모두의 시선이 머무는 라운지 한켠.
[7]  동아리방에는 혼자, 저녁 어스름이 밖에서 스며든다.
[11] 늦은 밤, 캠퍼스 골목. 따라오는 그림자 하나.
```

전부 **언제·어디** 표시다. 세계 설명 0회, 1인칭 내면 0회, 나중에 아는 사실 0회.
게다가 뒤 둘은 그림에 이미 보이는 것이라 "겹치지 마라" 규칙에도 걸린다.

**상류에 재료가 없었다.** `seed.json` 에는 세계관 텍스트가 통째로 들어 있는데
`build_engine_card` 가 그걸 싣지 않았다 — 엔진 카드에서 "세계" 라는 낱말이 0회였다.
그래서 5·7단계는 이 이야기가 **어떤 세계인지 모른 채** 썼고, 나레이션이 쓸 재료가
시간·장소밖에 없었다. 로판이라면 "엘젠하르트 제국" 같은 고유명사가 여기서 나와야 한다.

이제 카드에 `[장르]` · `[세계]` 블록이 실린다(`seed` 가 없는 옛 run 은 그대로 통과).
그리고 `w7.txt` 가 나레이션이 할 수 있는 일 다섯을 나눠 적는다.

| | 무엇 | 비고 |
| --- | --- | --- |
| ① | 시간·장소 표시 | **실제로 바뀔 때만.** 장면이 넘어간다고 매번 붙이지 않는다 |
| ② | 세계를 알려 준다 | 고유명사·제도·역사 — 그림으로 못 그리는 것. 1화라면 앞쪽에 한 번 |
| ③ | 주인공의 1인칭 독백 | `thought` 와 다르다 — 속마음은 그 순간, 나레이션은 지나고 나서 |
| ④ | 나중에야 알게 되는 사실 | 독자 우위 컷 |
| ⑤ | 인물의 처지·관계 | 그림으로는 안 보이는 것 |

**개수는 세지 않는다.** 하한을 두면 장면이 바뀔 때마다 배경 설명을 붙여 칸만
채운다 — 그게 바로 위 실패다. `prose_warnings` 가 보는 것은 **한 가지 일만 하고
있는가** 하나뿐이다: 나레이션이 셋 넘게 나왔는데 전부 `transition: 장면` 자리에만
있으면 그건 공식이지 연출이다.

### 2화가 물려받는 것 — 두 종류다

지금 만드는 것은 1화 하나지만, 1화의 결과물은 컷 목록만이 아니다. 다음 화가 받는
것은 **작품이 가진 것**과 **지나온 화가 쌓은 것** 둘로 나뉜다.

| | 무엇 | 어디에 | 프롬프트로 가는 길 |
| --- | --- | --- | --- |
| **작품이 가진 것** (안 바뀐다) | 로그라인 · 장르 배신 · RULE/COST/IRONY · 낙차 · 엔진급 질문 | `engine_card.txt` | 엔진 카드가 4~7단계 전 프롬프트에 원문 삽입 |
| | 주인공 · 「그 한 사람」 | 〃 | 〃 (화마다 재조립 — 아래 참조) |
| | **전체 줄거리 (Arc 전부)** | `arcs.json` | `{series_arc}` |
| **화가 쌓은 것** (늘어난다) | 인물 · 장소 · 확정된 설정 · 몸에 남은 자국 · **존(zone)** | `series.json` | `{series_state}` + 엔진 카드, 존은 7단계 `zones_block` 으로 별도 전달 |
| | 아직 열려 있는 질문 | `ledger.json` | `{ledger_snapshot}` |

**전체 줄거리가 빠져 있었다.** `arc_json` 은 그 화가 속한 Arc **하나뿐**이라, 2화를
쓰는 모델은 이 작품이 앞으로 어디로 가는지 모른 채 눈앞의 Arc 만 보고 썼다. 방향이
없으니 매 화가 제자리를 돌거나 이번 Arc 에서 다 터뜨리려 든다.

그렇다고 전 Arc 를 통째로 주면 반대쪽으로 고장 난다 — 17화를 한꺼번에 설계하던 시절에
17화치 떡밥을 1화에서 미리 스케줄링하다 부채가 쌓여 마지막 Arc 가 무너졌다. 그래서
`series_arc_block` 은 **한 줄씩만** 준다. 지도는 보이되 일정표는 못 짠다.

```
  Arc 1. 경계의 선 (전개 · 3화)
      시하가 공식 공간과 사적 공간을 나눈다. 윤재가 그 선을 넘는다.
  Arc 2. 예고 없는 침범 (반전 · 3화) ←  지금 여기
      사적 공간까지 넘어온다.
  Arc 3. 동경의 대가 (상승 · 4화)
      경계가 흐려진다.
```

**엔진 카드는 화마다 다시 만든다.** 인물은 P1 에서 끝나지 않는다 — 5단계가 화마다
사람을 추가하고 그 사람이 다음 화에도 나온다. 카드를 한 번 만들고 얼려 두면 3화에서
나온 인물이 7화 컷 설계에서 사라진다.

이 둘이 파일에는 늘 있었지만 사람이 열어 볼 일이 없어서 확인이 안 됐다. 그래서
`webtoon.md` 끝에 **"작품이 가진 것"** 과 **"다음 화가 물려받는 것"** 두 절로 찍는다.
여기가 비어 있으면 2화가 1화를 잊는다.

### 7단계 — 컷은 균일한 네모가 아니다

컷을 "화면에 보이는 것 + 대사"로만 서술하면 모든 컷이 같은 크기·같은 비율로 생성된다.
세로로 이어붙이면 웹툰이 아니라 **크기 같은 이미지의 나열**이 나온다. 실제 세로 스크롤
웹툰은 컷 크기·여백·시선 유도가 연출의 핵심이므로, 7단계 컷 하나에는 "무엇이 보이는가"와
"어떻게 놓이는가"가 함께 들어간다.

| 필드 | 값 | 정하는 주체 |
| --- | --- | --- |
| `shot` | 원경 / 전신 / 중간 / 바스트 / 클로즈업 / 익스트림 / 인서트 | **모델** — 무엇이 중요한가에서 나온다 |
| `angle` | 수평 / 부감 / 앙각 / 수직 / 기울임 | **모델** — 힘의 관계에서 나온다 |
| `transition` | 순간 / 동작 / 인물 / 장면 / 분위기 | **모델** — 직전 컷과의 관계 |
| `size` | wide(16:9) / normal(4:3) / tall(3:4) / impact(9:16) | **모델** — 내용에서 나온다 |
| `beat` | setup / build / turn / release / hold | **모델** — 독자의 상태에서 나온다 |
| `render_style` | normal / sd / emphasis / bleed / breakout | **모델** — 그림체와 칸 쓰기 |
| `description` | 화면에 보이는 것 (카메라 낱말 없이) | **모델** |
| `speaker` | 이 컷에서 말하는 사람 | **모델** — 대사가 있으면 필수 |
| `dialogue` `narration` `thought` `sfx` | 말풍선 / 나레이션 상자 / 속마음 / 효과음 | **모델** — 넷 중 골라 쓴다 |
| `gap_after` | 0~3 | 코드 — beat + transition 에서 계산 |
| `scene_break` | true/false | 코드 — hold·turn 자리 중 2~5컷 배분 |
| `gaze` | down / toward-next / at-viewer | 코드 — 거리·앵글·위치에서 계산 |

컷 위에 `scenes`(`what` · `mood` · `last_cut`) 가 있다. 장면 경계는 여기서 나온다 —
위 "장면이 먼저다" 참조.

모델이 컷마다 정하는 것은 여섯이다 — `shot` `angle` `transition` `size` `beat`
`render_style`. `w7.txt` 는 이 여섯을 **컷 서술보다 먼저** 수열로 뽑게 한다
(`beat_sequence` / `shot_sequence` / `angle_sequence` / `size_sequence`).
컷을 하나씩 쓰다 보면 매 컷이 "지금 누가 무엇을 말하는가"로 좁혀져 카메라가 얼굴 앞에
붙박이기 때문이다 — 그래서 자리를 먼저 확정하고 그 자리에 맞는 그림을 찾게 한다.

### 독자가 상황을 모른다 — 말의 밀도 (실측)

연출 단조로움보다 **앞선** 문제가 있었다. 같은 643컷을, 이번에는 `sfx` 를 빼고
말(대사·나레이션·속마음)만 세었다.

| 항목 | 실측 |
| --- | --- |
| 말 있는 컷 | **38% / 41% / 28%** |
| 말 없는 컷 최장 연속 | **12컷 / 11컷 / 10컷** |
| 화당 말 있는 컷 최소 | 1개 / 1개 / 1개 |
| 컷당 평균 글자수 | 9자 / 8자 / **5자** |
| 나레이션 총량 | 26 / 13 / **2개** (213컷 중) |

한 화가 12~13컷인데 말 없는 컷이 12연속이면 그 화는 통째로 무성영화다. 실제로
궁정 만찬 장면의 첫 컷(setup·wide)과 판이 뒤집히는 컷(turn·impact)에 둘 다 글자가
한 자도 없었다. 그림은 멀쩡한데 독자는 **여기가 어디고 무엇이 걸려 있는지** 알 수 없다.

처음에 이걸 놓친 이유는 네 칸(`dialogue`/`narration`/`thought`/`sfx`)을 한 덩어리로
셌기 때문이다. 그러면 "쿵" 하나 붙은 컷도 텍스트 있는 컷이 되어 침묵률이
38~69%로 보인다. **효과음은 상황을 설명하지 않는다.** 빼고 세니 58~71%였다.

원인은 프롬프트가 무성 쪽으로만 밀고 있었다는 것이다. 반대 방향 제동이 하나도 없었다.

  - "글자 없는 컷을 넣는다 — 최소 2개" (하한만, 상한 없음)
  - "특히 hold 컷은 대개 침묵이다" — `hold` 는 전체 컷의 24%다
  - "나레이션으로 그림을 때우지 마라" — 맞는 말이지만 *언제 써야 하는가*가 없었다
  - "전부 비어 있어도 된다(침묵 컷)"

침묵은 카드지 기본값이 아니다. 도쿄대 측정(Ikuta et al. 2023, Sci Rep)에 따르면
패널 체류 시간은 그림 크기가 아니라 **말풍선 텍스트 길이에 비례**한다 — 글자가
없으면 큰 컷을 놓아도 독자는 그냥 지나간다. `docs/webtoon_directing_reference.md`
가 이걸 "아이러니한 실증 결과"로 따로 적어 두고 있다.

`gate_text()` 가 네 가지를 센다. 밀도 둘, 자리 둘이고 **자리 쪽이 더 중요하다** —
첫 컷과 장면이 바뀌는 컷은 독자가 길을 잃는 지점이라, 거기가 비면 나머지가 아무리
촘촘해도 소용이 없다.

| 조건 | 값 |
| --- | --- |
| 말 있는 컷 비율 | 50% 이상 (`MIN_SPEECH_RATIO`) |
| 말 없는 컷 연속 | 2컷까지 (`MAX_MUTE_RUN`) |
| 첫 컷 | 말 필수 |
| `transition: 장면` 컷 | 말 필수 — 나레이션이 원래 할 일이 이것이다 |

여기서 세는 것은 **말이 있는가**뿐이다. 대사든 나레이션이든 속마음이든 상관없다.
`speaker` 필드를 새로 두어 대사가 있는 컷은 화자를 밝히게 했다(그림 단계가 말풍선을
누구에게 붙일지 알아야 한다). 나레이션·속마음만 있는 컷은 화자가 비어도 된다.

### 비율은 세지 않는다 (게이트에서 뺀 것들)

한동안 말 밀도·sd 개수·침묵 컷 개수를 게이트로 막았다. 실측이 험했기 때문이다 —
말 있는 컷 28~41%, 말 없는 컷 최장 12연속. 막으니 숫자는 맞았다.

그런데 **비율을 강제하면 모델은 비율을 맞춘다.** 이야기가 부르는 대로가 아니라
숫자가 부르는 대로 대사를 넣고 SD 를 올린다. 무성으로 밀어붙이는 화도, 나레이션
하나로 굴러가는 화도, 개그가 이어져 SD 가 여덟인 화도 전부 정답일 수 있는데
그 답이 막힌다. 그래서 **세되 막지 않는다.**

| 항목 | 예전 | 지금 |
| --- | --- | --- |
| 말 있는 컷 비율 | 게이트 50% | `text_warnings` |
| 말 없는 컷 연속 | 게이트 2컷 | `text_warnings` (4컷부터 메모) |
| 첫 컷·장면 전환 컷의 말 | 게이트 | `text_warnings` |
| 침묵 컷 개수 | 경고 하한 | 개수는 안 본다 |
| sd·통컷·칸밖 **개수** | 게이트 + 자동 강등 | `render_warnings` |
| 나레이션 개수 | (넣으려다 뺌) | 안 본다 |

**자리는 남겼다.** sd 를 turn 에 쓰면 그 순간이 가벼워지고, 스팅어를 SD 로 끝내면
훅이 풀린다. 통컷은 turn·release, 칸밖은 build·turn·release. 이건 "몇 개냐" 가
아니라 "여기냐" 라서 이야기가 달라져도 답이 같다.

`repair_render_styles` 의 개수 강등도 없앴다. 코드가 여섯 번째 sd 를 조용히
normal 로 내리면, 그 화가 왜 심심해졌는지 아무도 모른다.

> 카메라 쪽 비율(얼굴 55% · 수평 앵글 70% · impact 2개 · 기울임 2개 · 전환 3종)은
> 게이트로 남겨 두었다. 그건 처음 진단한 "컷이 단조롭다" 를 막는 장치이고 —
> 클로즈업+바스트 60%가 그 증거다 — 텍스트 비율과 달리 **이야기가 달라져도
> 얼굴만 60% 나오는 화가 좋아지지는 않기** 때문이다. 이것도 풀고 싶으면 말해 달라.

### 게이트에 넣을 것과 경고로 남길 것

말 밀도를 세기 시작하면서 규칙을 계속 늘리게 되는데, 그러면 온도 0.9 에서 조건이
서로 얽히고(이 문서 여러 곳에 그 실패 이력이 있다) 무엇보다 **모델이 규칙만 채우고
연출은 오히려 뻣뻣해진다.** 그래서 기준을 하나 세웠다.

| 종류 | 예 | 처리 |
| --- | --- | --- |
| **상한·편중** | 얼굴 55%, 수평 70%, impact 2개, 같은 값 4연속, 통컷 1개 | 게이트 |
| **수단을 열어 둔 하한** | 말 있는 컷 50%, 첫 컷·장면 전환 컷에 말 | 게이트 |
| **데이터 완결성** | 값이 목록에 있는가, 대사에 `speaker` 가 있는가 | 게이트 |
| **특정 수단을 못 박는 하한** | 인서트 1개, 원경 1개, `분위기` 전환 1개, 대사 주고받기, 화자 2명 | **경고** |

마지막 줄이 핵심이다. "대사가 2컷 이상 오가야 한다", "말하는 사람이 둘 이상이어야
한다" 를 게이트로 두었다가 뺐다 — **혼자 말하는 화도 정답이기 때문이다.** 혼잣말은
말풍선이 아니라 `thought` 나 나레이션으로 쓰면 되고, 1인칭 나레이션으로 굴러가는
웹툰은 아주 흔하다. 수단을 강제하면 그 답을 없애게 된다.

같은 이유로 "인서트 최소 1개" 같은 것도 게이트에서 뺐다. 화마다 맞는 답이 다르고,
강제하면 모델이 자리를 만들어 끼워 넣는다 — 개수는 맞고 장면은 어색해진다.
관찰은 그대로 `prose_warnings` 가 남긴다. 사람이 보고 판단할 몫이다.

`w7.txt` 5-7 절도 그에 맞춰 **수단 넷을 나란히** 놓았다: 주고받기(사람이 여럿일 때) ·
나레이션(혼자 있을 때) · 속마음(혼잣말) · 인서트(소품이 말하게). 어느 것으로 풀어도
된다고 적고, 대신 "이 장면을 처음 보는 사람이 상황을 알 수 있는가" 를 묻게 했다.

**과거 산출물 51화가 전부 이 게이트에 걸린다** (`speaker` 49회 · 3연속 43회 ·
밀도 41회 · 첫 컷 21회). `speaker` 는 옛 데이터에 없던 필드라 당연하고, 나머지
셋이 실제 내용 문제다. 그래서 7단계 재시도 예산을 화 단위로 바꿨다 — 아래를 볼 것.

### 7단계 재시도 예산은 화마다 (버그 수정)

`run_webtoon` 이 `solve_cuts(..., spent=result.regen_stage7)` 로 **실행 전체의 누적**을
넘기고 있었다. `--max-retries` 기본값이 2이므로, 17화짜리 실행에서 1화가 두 번
되돌아가면 나머지 16화는 예산이 0이 된다. 게이트가 느슨할 때는 드러나지 않았고
(실측 stage7 재생성 0~2회) 실제로 걸린 적이 없었지만, 얼굴 비율·말 밀도까지 세면
그 구조로는 2화를 못 넘긴다.

`--cuts-only` 는 원래 화마다 예산을 주고 있었다. 두 경로가 어긋나 있던 것을 맞췄다.
4·5단계는 그대로 실행 전체다 — 거기는 단위가 Arc(4~6개)라 같은 문제가 없다.

> 비용 영향: 7단계 최악의 경우가 `화 수 × (1 + max_retries)` 호출로 늘어난다.
> 17화·재시도 2면 19회 → 최대 51회. 게이트가 처음부터 통과하면 예전과 같다.

### 카메라를 세 축으로 나눈 이유 (실측)

처음에는 카메라를 **서술 첫머리에 낱말 하나**로 적게 했다 — 익스트림 클로즈업 /
클로즈업 / 바스트 / 전신 / 부감 / 앙각. 완성된 run 3개(643컷)를 세어 보니 이랬다.

| 항목 | 실측 |
| --- | --- |
| 클로즈업 + 바스트 | **60%** (72+59 / 64+63 / 62+56) |
| 익스트림 클로즈업 | 0.5~2% (1 / 3 / 4컷) |
| 앙각 | 1~4% (8 / 2 / 7컷) |
| 서술에 카메라가 아예 없음 | 10~17% |
| 서술이 `wide.` `normal.` 처럼 size 로 시작 | **49% / 64% / 100%** |

두 가지가 동시에 고장 나 있었다.

**① 낱말 6개에 거리와 앵글이 한 축에 섞여 있었다.** 앵글은 부감·앙각 둘뿐이라
사실상 축이 죽어 있었고, 나머지는 전부 거리였다. 그래서 실제 선택은 "얼마나
가까이"로만 좁혀졌고, 대화가 이어지는 화에서는 그 답이 언제나 얼굴이었다.
말하는 얼굴 다음에 듣는 얼굴 — 각 컷은 멀쩡한데 화 전체가 밋밋했다.

**② 서술 첫머리라는 자리가 지켜지지 않았다.** 경고만 있고 게이트가 없어서
size 값을 적은 컷이 절반을 넘어도 그냥 통과했다. 한 run 은 13컷 전부가 그랬다.

그래서 **서술에서 빼내 필드로 분리하고 축을 나눴다.** 필드가 되면 ②는 구조적으로
불가능해지고(값이 목록에 없으면 게이트가 잡는다), ①은 축마다 따로 셀 수 있다.
`인서트`(인물이 아닌 것)를 거리 목록에 넣은 것이 핵심이다 — 인물 없는 컷에 이름이
없으면 모델은 그런 컷을 아예 만들지 않는다.

지금 게이트가 세는 것: 얼굴 거리(바스트·클로즈업·익스트림) 55% 이하, 인서트 최소 1개,
원경 최소 1개, 같은 거리 4연속 금지, 수평 앵글 70% 이하, 기울임 2개 이하,
전환 3종 이상 + `분위기` 최소 1개 + 같은 전환 4연속 금지 + 첫 컷은 `장면`.

### 색은 hex 로 — 두 하네스가 같은 색을 써야 한다

`color_palette` 값은 **영문 이름 + hex** 다: `bright gold (#F0C44C)`.
한글 색이름("밝은 금색")으로 두면 두 가지가 깨진다.

  - 시트 프롬프트의 나머지는 전부 영문인데 색만 한글이면, 그 자리만 이미지 모델의
    짐작에 맡기는 것이 된다.
  - webtoon-harness 는 `p1.json` 의 `color_palette` 를 **그대로** 컷 프롬프트에 박는다
    (`charsheet.py` 의 `PALETTE_HEAD`). 여기 형식이 곧 컷의 형식이다. 두 하네스가 다른
    형식으로 색을 지정하면 같은 인물이 두 색으로 나온다.

그래서 P1 이 처음부터 hex 로 내게 하고(`gate_visual` 이 hex 없는 칸을 반려한다),
그 전에 만들어진 카드를 위해 `--charsheet` 가 한글 색이름을 영문+hex 로 바꾼다.
`밝은 금색 → bright gold (#DFC369)`, `창백한 살구 → pale apricot (#F9E5D7)`.
수식어(밝은·연한·짙은·어두운·바랜)는 기준색을 밀어서 만든다 — 밝게 할 때는 곱하지 않고
흰색 쪽으로 섞는다. 곱하면 밝은 색이 금방 255 에 닿아 "창백한 살구"가 그냥 흰색이 된다.

사전에 없는 색은 **원문을 남기고 경고한다.** 아무 색이나 집어넣는 것보다 사람이 보고
고치는 편이 낫다. 엔진 카드에 싣는 팔레트도 같은 변환을 거친다 — 시트와 컷이 같은
값을 봐야 한다.

### 캐릭터 시트 — P1 외형 사양에서 시트 이미지로

```
python story.py --charsheet --run-id <id> --dry-run   # 프롬프트만 (0원)
python story.py --charsheet --run-id <id>             # Gemini · 1장 x 후보 2장 = 2회
python story.py --charsheet --run-id <id> --split     # 3종 x 후보 2장 = 6회
python story.py --charsheet --run-id <id> --provider openai --quality high
python story.py --charsheet --run-id <id> --pick      # 후보 채택 화면
```

**시트는 컷과 같은 모델로 뽑는다.** 기본이 Gemini 인 이유가 그것이다. 처음에는
OpenAI(`gpt-image-1`)로 뽑았는데 얼굴 비율이 크고 이목구비가 웹툰 양식이 아니었고,
더 큰 문제는 컷을 Gemini 가 그린다는 점이었다 — 같은 스타일 문구를 넣어도 두 모델의
그림체가 어긋나면 그 시트를 레퍼런스로 쓰는 의미가 없다. 비교해 볼 수 있게 OpenAI
경로는 `--provider openai` 로 남겨 두었고, 그 경우에만 그림체 경고가 뜬다.

| provider | 모델 | 경로 | 단가 |
| --- | --- | --- | --- |
| `gemini` (기본) | `GEMINI_IMAGE_MODEL` (기본 `gemini-2.5-flash-image`) | webtoon-harness 의 `providers/` 를 그대로 빌려 쓴다. 없으면 `google-genai` 로 대체 | webtoon-harness `config.yaml` 의 `cost_per_image_usd` |
| `openai` | `OPENAI_IMAGE_MODEL` (기본 `gpt-image-2`) | `openai` 패키지. `--quality low/medium/high` | 1536x1024 medium 기준 $0.041 |

컷을 그리는 **같은 코드**로 시트를 뽑는 것이 요점이다. 여기서 따로 구현하면
재시도·응답 파싱이 조금씩 달라지고, 그 차이가 그림 차이로 나타난다.
`gpt-image-1` 은 2026-10-23 종료 예정이라 OpenAI 기본값은 `gpt-image-2` 다.

### 뽑기 전에 사람이 외형을 본다

`--charsheet` 는 이미지를 부르기 전에 `appearance_en` / `design_details` /
`color_palette` / `expression_set` 을 콘솔에 펼쳐 보이고 **이 외형으로 진행할까요?** 를
묻는다. 아니오면 `p1.json` 의 어느 칸을 고치면 되는지 안내하고 멈춘다.

외형이 마음에 안 드는 것은 게이트가 잡을 수 없다 — 규칙 위반이 아니라 취향이기
때문이다. 이미지를 부르기 전에 사람 눈에 한 번 보이는 것이 유일한 방법이고, 여기서
멈추는 편이 뽑고 나서 버리는 것보다 싸다. (`--yes` 로 건너뛸 수 있다.)

시트를 story-harness 가 만드는 이유는 **외형 사양이 P1 에서 나오기 때문**이다.
사양을 만든 쪽이 시트까지 만들고, webtoon-harness 는 완성된 시트를 받아 쓰기만 한다.
두 하네스가 각자 시트를 만들면 같은 인물이 두 벌 생긴다.

**기본은 한 장이다.** 실제 캐릭터 시트가 그렇게 생겼고, 호출도 1/3 로 준다.
1536x1024 한 장에 네 영역을 배치한다 — 영역 사이에 여백을 두고 각각이 따로 읽히게.

| 영역 | 자리 | 내용 |
| --- | --- | --- |
| 1 | 상단 | 4면도(정면·3/4·측면·후면) 가로 한 줄. 한 지면선 위에서 키·비율 일치 |
| 2 | 중단 | 얼굴 클로즈업 표정 6종 가로 한 줄 (`expression_set` 을 그대로) |
| 3 | 하단 좌측 | `design_details` 항목별 확대 인셋 |
| 4 | 하단 우측 | `color_palette` 색상 칩 가로 한 줄 |

**`--split` 은 남겨 두었다.** 이미지 모델은 한 장 안에 요구가 많을수록 각각을 뭉갠다.
4면도의 비율이나 디테일 확대가 뭉개지면 쪼개서 다시 뽑을 수 있어야 한다.

| 시트 | 크기 | 내용 |
| --- | --- | --- |
| `turnaround` | 1536x1024 | 4면도, 무표정 차렷 |
| `expressions` | 1536x1024 | 표정 6종 가로 배열 |
| `details` | 1024x1024 | 고정 요소 확대 + 색상 칩 |

**통합 시트는 이제 그대로 넘어간다.** webtoon-harness 의 `charsheet.py` 가 `sheet`
키를 알고, 그 한 장을 붙이는 조건 `S` / `S+` 가 생겼다. `--split` 없이 뽑은 통합
시트를 채택하면 그쪽에서 바로 쓴다:

```bash
python story.py --charsheet --run-id <id>          # 통합 → 조건 S / S+
python story.py --charsheet --run-id <id> --split  # 3장  → 조건 C / C+ / D
```

시트가 없는데 그 조건을 부르면 **API 호출 전에 멈춘다.** 예전에는 `config.yaml`
의 `refs` 로 조용히 떨어졌고, 그 자리에 지난 run 의 시트가 남아 있어서 다른 사람
얼굴로 한 화가 통째로 그려진 적이 있다. 그 폴백은 없앴다.

`design_details` 와 `expression_set` 은 **번역하지 않고 한국어 그대로** 싣는다.
"왼쪽 소매의 노란 반사띠" 를 "yellow stripe" 로 옮기면 위치가 사라져서 고정 요소가
고정이 아니게 된다. 뼈대 지시만 영문으로 준다.

호출 전에 P1 사양을 검사한다(`gate_charsheet_source`). 사양 없이 이미지를 부르면 모델이
빈칸을 학습 데이터 평균값으로 채우고, 그렇게 나온 시트는 "컷마다 다른 사람"을 막지
못한다 — 돈만 쓰고 끝난다. 그래서 호출 전에 세운다.

**스타일 문구는 webtoon-harness 가 원본이다.** `webtoon-harness/config.yaml` 의
`style_suffix` 를 읽어서 프롬프트 맨 끝에 붙인다(컷 쪽 `prompt_template` 의
`{appearance} {scene} {style} {extra}` 와 자리를 맞춘다). 값이 story-harness 의
`EXPECTED_STYLE_SUFFIX` 와 다르면 **webtoon-harness 값을 쓰고 경고한다** — 컷을 그리는
쪽이 원본이기 때문이다. 설정을 못 찾으면 기준값으로 진행하되 역시 경고한다.
경로는 `.env` 의 `WEBTOON_HARNESS_DIR` 로 바꿀 수 있다.

이미지 생성은 텍스트보다 비싸므로 실행 전에 호출 수와 예상 비용을 보여주고 y/N 을
묻는다. `.env` 의 `IMAGE_COST_USD` 로 단가를 덮어쓸 수 있다. 모르는 단가는 적지 않는다 —
모르는 숫자를 적어 두면 비용 표시가 거짓말이 된다. 키가 없으면 실제 생성은 중단하고
`--dry-run` 을 안내한다.

**캐릭터 시트는 기본이 통합 한 장**이다 (`sheet_c1.png`). 그 한 장 안에 4면도 ·
표정 6종 · 디테일 · 컬러 팔레트가 네 구역으로 들어 있고, webtoon-harness 의
조건 **`S`** 가 그대로 읽는다.

```
python story.py --charsheet --run-id {run_id}          # 통합 시트 1장 (호출 1회)
cd ../webtoon-harness
python run.py --run-id {run_id} --episode 1 -c S       # 그 시트로 컷 그리기
```

`--split` 을 붙이면 turnaround · expressions · details 세 장으로 쪼개지고, 그때는
조건 `C+` 를 쓴다. 담는 정보는 같지만 호출이 3배이고, 세 장을 따로 그리므로 시트끼리
그림체가 흔들릴 수 있다.

**화풍은 `webtoon-harness/config.yaml` 의 `styles` 에서 온다.** 현재 `webtoon`(일반
웹툰 — 깔끔한 선, 셀 채색, 읽히는 속도 우선) · `romance`(로맨스 표지 일러스트 — 화려한
채색, 디테일한 눈동자·머리카락) · `flat`(평평한 색, 최소 음영) 셋이고 기본값은
`romance` 다. 시트를 컷과 **같은 화풍**으로 뽑아야 레퍼런스로 쓸모가 있으므로 이
저장소는 그 문구를 읽어서 그대로 붙인다 — 값이 다르면 경고한다.

산출물:

```
runs/{run_id}/charsheet/sheet_c{k}.png                 통합 (기본)
                        {turnaround,expressions,details}_c{k}.png   --split
                        {kind}_prompt.txt      실제로 보낸 프롬프트
                        charsheet_meta.json    모델·스타일 문구·출처 · 실제 장수와 비용
                        pick.html              후보 채택 화면
                        charsheet_picks.json   확정 결과
```

`[확정]` 을 누르면 `charsheet_picks.json` 과 **`runs/{run_id}/meta.json` 의 `charsheet`
키**에 절대 경로가 기록된다. webtoon-harness 는 `refs/` 로 복사하지 않고 이 경로를
그대로 참조한다 — 복사본이 생기면 시트를 다시 뽑았을 때 어느 쪽이 진짜인지 알 수 없다.
`pick.html` 은 서버로 열면 곧바로 저장되고, 파일로 열면 JSON 을 내려받는다.

**이미 뽑은 시트는 다시 부르지 않는다.** `charsheet_meta.json` 이나
`charsheet_picks.json` 이 그 폴더에 있으면 `--charsheet` 는 곧바로 "이미 있습니다"
라고 찍고 끝난다 — 그림 단계 명령을 짤 때마다 앞에 `--charsheet` 를 다시 붙여도
매번 돈이 나가지 않는다. 다시 뽑으려면 그 폴더(`charsheet/`)를 사람이 직접 지운다.

### 조연 시트 — 주연만, 캐릭터 시트가 아예 없던 조연에게

지금까지 시트는 **주인공 1명 전용**이었다. 조연은 `series.json` 의 명부에
`gender/appearance/outfit/personality` 네 줄만 있고, 이미지 기준선이 없어서 컷마다
비율·복장이 흔들렸다 — 특히 "그 한 사람"(엔진 카드의 관계 예외 인물, 예: 하윤재)처럼
자주 나오는 인물일수록 손해가 컸다. 그렇다고 등장하는 조연 전원에게 시트를 뽑지는
않는다 — 그건 비용 대비 효과가 낮고, 이 파이프라인은 주연 둘(주인공 + 그 한 사람)의
얼굴이 안 흔들리는 것만으로 웹툰 하네스 피드백의 대부분이 사라진다.

```bash
python story.py --charsheet --run-id <id> --second-lead --dry-run   # 프롬프트만 (0원)
python story.py --charsheet --run-id <id> --second-lead             # 실제 생성
```

**전제**: 최소 1화가 만들어져 있어야 한다. "그 한 사람"의 외형은 `p1.json` 처럼 손으로
채워진 곳이 없다 — 이름과 "왜 그 사람만 예외인가" 한 줄만 엔진 카드에 있고, 실제
gender/appearance/outfit/personality 는 그가 처음 등장하는 화의 **5단계(W5)**가
`new_cast` 에 채운다. 그래서 `--second-lead` 는 `webtoon/series.json` 의 명부에서
그 이름을 찾고, 네 항목이 다 채워져 있는지 먼저 확인한다 — 없으면 어느 화를 먼저
만들어야 하는지 안내하고 멈춘다.

내부적으로 두 단계다:

1. **외형 사양 만들기** (`solve_lead_appearance`, 새 프롬프트 `prompts/lead_appearance.txt`) —
   명부의 짧은 네 줄을 P1 스키마와 같은 형태(`appearance_en` · `design_details` 3~5개 ·
   `color_palette` 6칸 · `expression_set` 6종)로 확장하는 LLM 호출 1회. 주인공의
   `appearance_en` 을 같이 보여줘서 색·고정 요소가 겹치지 않게 한다. 결과는
   `runs/{run_id}/charsheet_2nd/lead.json` 에 캐시된다 — **이미 있으면 다시 호출하지
   않는다.**
2. **시트 이미지 생성** — 위 사양으로 `run_charsheet()` 를 그대로 재사용하되, 저장
   위치만 `charsheet_2nd/` (주인공의 `charsheet/` 와 섞이지 않는 형제 폴더)로, `meta.json`
   의 기록 키만 `charsheet_second_lead` (주인공의 `charsheet` 키를 덮어쓰지 않도록)로
   바꾼다. 이 단계도 이미 만든 시트가 있으면 건너뛴다.

```
runs/{run_id}/charsheet_2nd/lead.json          외형 사양 (appearance_en 등)
                            sheet_c1.png        캐릭터 시트 이미지
                            charsheet_meta.json / charsheet_picks.json
```

webtoon-harness 는 `charsheet.load_second_lead()` 로 이 폴더를 읽어, 그 인물이 실제로
나오는 컷/장면에만 이 시트를 첨부한다 (주인공 시트와 독립적으로 판정된다).

### 존 배경 자산 (`--zonesheet`)

배경도 지금까지는 컷마다 자유 텍스트로 다시 그려졌다. 7단계가 이제 컷마다 `zone`
(구역 id)을 붙이므로, 같은 구역은 배경 1장을 만들어 재사용할 수 있다.

```bash
python story.py --zonesheet --run-id <id> --dry-run   # 프롬프트만 (0원)
python story.py --zonesheet --run-id <id>              # 아직 배경이 없는 존만 생성
```

`series.json` 의 `zones[]` 에 등록된 존마다 배경 1장을 뽑는다. **사람이 미리 채울
칸이 없다** — `zone_id` 도 그 존의 `label`(배경 서술)도 7단계가 만들고, `gate_zone`
이 이미 검사한 것이다. 이미 배경이 있는 존은 건너뛴다 — 다시 뽑으려면
`runs/{run_id}/zonesheet/<zone_id>/` 폴더를 지운다. 채택 화면은 없다 — 후보 1장이
기본이라 `bg_c1.png` 를 그대로 쓰고, 경로는 `meta.json` 의 `zonesheet` 키에 남는다.

webtoon-harness 는 `charsheet.load_zonesheet()` 로 이 자산을 읽어, 묶인 컷이 전부
같은 존일 때만(`scenegen.scene_zone`) 그 배경을 레퍼런스로 첨부한다. 컷마다 존이
갈리는 Scene 에는 붙이지 않는다 — 배경 하나를 잘못 붙이는 것이 안 붙이는 것보다
나쁘다.

### 존 검수는 그림이 아니라 **글**에서 한다 (`gate_zone`)

존 배경은 한 번 구우면 그 존의 **모든 컷이 재사용**한다. 그래서 잘못된 배경 하나가
화 전체로 번지고, 이미지를 뽑은 뒤에 알면 그 존의 컷이 전부 다시다. 그래서 검수를
이미지 뒤에 두지 않는다 — 7단계가 `zones[]` 로 "그 자리가 **사람 없이** 어떻게
생겼는가"를 적고, 그림을 부르기 전에 코드가 본다. 셋 다 필드 대조라 LLM 도 문자열
매칭도 필요 없다.

| 검사 | 왜 |
| --- | --- |
| 컷의 `zone` 이 비어 있지 않은가 | 없으면 배경을 붙일 수 없다 |
| 컷이 가리키는 새 존의 서술이 `zones[]` 에 있는가 | 없으면 그 배경은 안 그려진다 |
| **그 서술에 사람이 없는가** | 인물이 들어가면 그 사람이 배경에 구워져 그 존의 모든 컷에 따라다닌다 |

세 번째가 핵심이다. 처음에는 존의 `label` 로 **컷 서술을 그대로 가져다 썼는데**,
컷 서술은 그 순간을 적은 것이라 사람과 동작이 들어 있다("소파에 시하가 앉아
휴대폰을 본다"). 그것을 배경 프롬프트로 쓰면 시하가 배경에 구워진다. 그래서 배경
서술을 별도 필드로 분리하고 여기서 검사한다. 이름 대조는 **성을 뗀 형태까지**
본다(`name_variants`) — "하윤재"만 찾으면 "윤재가 앉아 있다"를 한 번도 못 잡는다.

이미 배경이 있는 존은 서술을 다시 요구하지 않는다. 다시 적으면 조금씩 달라지고,
그 순간 같은 자리가 두 개의 배경을 갖게 된다.

### 소품 장부는 두지 않는다

"자판기에서 머그컵이 나온다" 같은 사고를 소품을 하나씩 등록해 매 컷 대조하는
방식으로 막지 않는다. 그 검사는 컷마다 수십 건씩 판정을 만드는데 진짜 오류는
회당 한둘이라, 노이즈에 묻혀 아무도 검사 결과를 안 보게 된다 — 그러면 검사기가
없는 것과 같다.

**존 배경이 그 자리를 대신한다.** 자판기가 `z-hallway-vending` 배경에 한 번
그려지면 그 뒤 그 존의 컷은 전부 그 배경을 참조하므로, 머그컵이 새로 생길 경로
자체가 없다. 이미 막힌 구멍에 뚜껑을 하나 더 대지 않는다.

자산층은 **캐릭터 시트 + 존 배경 둘뿐**이다. 이야기상 중요한 물건(주고받는 편지,
잃어버린 반지)은 소품 일관성 문제가 아니라 **서사·상태 문제**라서, `state_changes`
와 같은 층에서 따로 설계한다.

### P1 외형 고정 설계 — 컷마다 같은 사람이 나오게 하는 자리

이미지 모델은 **안 쓰인 칸을 매번 다르게 그린다.** 그래서 "무엇이 고정인가"를 P1 에서
다 못 박는다. 여기가 비면 그 자리가 컷마다 흔들린다.

| 필드 | 내용 | 게이트 |
| --- | --- | --- |
| `appearance` | hair / eyes / build / clothing / impression / element (한국어) | 여섯 칸 전부 |
| `appearance_en` | 이미지 생성용 영문 한 문단. webtoon 하네스의 `character_appearance` 로 그대로 들어간다 | 한글 혼입 반려 · 80자 이상 · 머리/눈/체형/복장 |
| `design_details` | 매 컷에 유지될 물리적 특징 3~5개 | 개수 · 추상어("우아한 분위기") 반려 |
| `color_palette` | hair / eyes / skin / outfit_main / outfit_sub / accent. **영문 이름 + hex** (`bright gold (#F0C44C)`) | 여섯 칸 전부 · hex 없으면 반려 |
| `expression_set` | 이 이야기에서 실제로 짓는 표정 6종 | 정확히 6개 · 감정 이름만이면 반려 |
| `visual_hook` | 첫 컷에서 멈추는 이유 한 문장 | 평가어(잘생김·예쁨·매력적) 반려 |

`element` 는 사용자가 준 목록에 없지만 **뺄 수 없다.** 블라인드 카드 시험(`card_view`)이
샘플 카드와 이 칸을 나란히 놓고 비교하기 때문에, 여기가 비면 생성 카드만 빈칸이라
내용을 보기 전에 골라진다. 그래서 `appearance` 는 6칸이다.

**`expression_set` 은 카드 장식이 아니라 7단계의 어휘 목록이다.** 엔진 카드에 실려
컷 서술로 넘어가고, 컷은 "불안한 표정" 같은 추상어 대신 여기 적힌 서술을 옮겨 쓴다.
7단계에 "감정은 눈에 보이는 것으로만" 규칙을 넣어도 어휘가 없으면 컷마다 흔들린다 —
`겁먹음 — 동공이 커지고 턱이 굳는다` 가 미리 정해져 있으면 흔들리지 않는다.

`design_details` / `color_palette` / `appearance_en` 도 같은 이유로 엔진 카드에 싣는다.
새 필드가 없는 옛 run 은 해당 절이 **아예 실리지 않는다** — 빈 목록을 실으면
"아래에서 골라 쓰라"는 지시가 빈칸을 가리키게 되고, 모델은 그 자리를 학습 데이터
평균값으로 채운다.

### 칸을 어떻게 쓰는가 (bleed / breakout)

세로 스크롤에서만 되는 연출 둘을 `render_style` 에 넣었다. 그림체가 아니라 칸 쓰기지만,
컷 하나에 붙는 배타적 선택이라는 점이 같다. 축을 더 늘리면 온도 0.9 에서 서로 얽힌
조건이 다시 폭발한다(아래 "여섯 번 연속 실패" 참조).

| 값 | 무엇 | 상한 | 허용 beat |
| --- | --- | --- | --- |
| `bleed` | 통컷. 테두리가 없고 그림이 화면 가장자리까지 찬다. 칸이라는 것이 사라진다 | 화당 1개 | turn / release |
| `breakout` | 인물·사물의 일부가 테두리를 뚫고 여백으로 튀어나온다 | 화당 2개 | build / turn / release |

`bleed` 를 화당 1개로 묶은 이유는 실무 가이드가 한결같이 말하는 것이다 — 두 번째
통컷은 "블록버스터 순간"이 아니라 그냥 큰 그림이다. 그리고 `derive_layout` 이
**통컷 직전에 최대 여백을 넣는다.** 빈 화면을 지나 통컷이 펼쳐지는 것이 세로 스크롤에서
가장 센 카드라, 그 여백은 코드가 보장해 준다.

### 컷마다 바뀌는 그림체 (render_style)

실제 웹툰은 한 화 안에서 그림체가 고정되지 않는다. 진지한 장면은 정식 작화로 그리다가,
분위기를 푸는 자리에서 갑자기 2~3등신으로 바뀐다. **그 전환 자체가 리듬이다.** 전부 같은
그림체로 그리면 잘 그린 삽화집이지 웹툰이 아니다.

| 값 | 무엇 | 게이트 |
| --- | --- | --- |
| `normal` | 기본 작화 | — |
| `sd` | 2~3등신 데포르메. 얼굴 단순화, 파스텔 배경, 별·하트·땀방울 | 화당 **최대 5컷(하한 없음)** · `beat` 가 release/hold/build 인 컷에서만 · 마지막 컷 금지 |
| `emphasis` | 배경 생략, 인물만, 집중선 | 개수 제한 없음 |

`turn` 을 SD 로 그리면 중요한 순간이 가벼워진다. 터진 뒤(release)와 멈춘 자리(hold)가
기본이고, 쌓는 중(build)에도 한 컷씩 가볍게 빠질 수 있다 — 실제 웹툰에서 흔한 리듬이다.
처음 세우는 자리(setup)와 뒤집는 순간(turn)은 안 된다. 스팅어를 데포르메로 그리면 훅이
풀린다.

**하한은 두지 않는다.** 한때 "화당 3컷 이상" 을 강제했는데, 그러면 모델이 자리를
채우려고 진지한 컷을 데포르메로 올린다 — 개수는 맞지만 그 장면이 가벼워진다. SD 는
장면이 부를 때 나와야 한다: 긴장이 풀리는 리액션 컷, 개그·당황, 분위기 전환. 그런
자리가 없는 화도 있고, 진지한 장면이 끝까지 이어지면 **0개인 것이 맞는 답**이다.
상한만 남긴다 — 데포르메가 너무 잦으면 산만해지고, 정식 작화로 돌아왔을 때의 무게가
사라진다.

**코드는 강등만 한다.** sd 를 normal 로 내리는 것은 "이 컷은 특별하지 않다" 는 뜻이라
안전하지만, 어떤 컷을 SD 로 **올릴지**는 톤 판단이라 코드가 정할 수 없다. 승격은 아예
하지 않는다 — 서술이 그림체에 묶여 있어서(w7 규칙 8), "눈동자에 미묘한 떨림이 감돈다"
를 그대로 두고 `render_style` 만 `sd` 로 바꾸면 그림체 지시와 서술이 정면으로 부딪친다.

webtoon-harness 쪽은 `config.yaml` 의 `render_style_suffix` 에서 값별 문구를 읽어
`style_suffix` **바로 뒤**에 붙인다(코드가 박고 LLM 도 템플릿도 뺄 수 없다).
sd 도 캐릭터 시트 첨부는 그대로 둔다 — 같은 인물이라는 것은 시트가 잡아 주고
여기서는 등신만 바뀌기 때문이다.

### SD 가 한 컷도 안 나오던 이유 — 장면 `tone`

실측: 13컷 전부 `normal`. 원인은 규칙이 없어서가 아니라 **신호가 없어서**였다.
`render_style` 은 컷마다 정해지는데, 컷을 쓰는 시점에 "이 장면이 웃긴 장면인가"를
아무도 말해 주지 않는다. 게다가 프롬프트는 (옳게) *"sd 개수를 세지 마라"* 라고
가르치므로, 신호가 없으면 모델은 안전한 `normal` 로 수렴한다. **정상 동작이다.**

그래서 고치는 방향이 중요하다. 하한("sd 3컷 이상")을 넣으면 이 저장소가 두 번
걷어낸 비율 게이트가 돌아온다 — 개수는 맞고 장면은 가벼워진다. 대신 **신호**를
준다: 7단계가 장면마다 `tone` 을 적는다.

| `tone` | 막히는 것 | 왜 |
| --- | --- | --- |
| `개그` | — | sd 를 적극적으로 쓰는 자리. 여기서 sd 가 하나도 없으면 대개 놓친 것이다 |
| `일상` | — | 리액션이 있으면 쓴다 |
| `긴장` | **sd 금지** | 조여진 공기를 데포르메로 그리면 그 순간이 풀린다 |
| `감정` | **sd 금지** | 속이 드러나는 얼굴은 정식 작화로 그린다 |

**허용 목록이 아니라 금지 목록인 것이 요점이다.** 허용으로 쓰면 "개그면 sd 를 써야
한다"가 되어 다시 할당량이 된다. `repair_tone_lock` 은 **강등만** 한다 —
`repair_render_styles` 와 같은 이유로 승격은 하지 않는다.

`tone` 을 **W5 가 아니라 W7 에 둔 이유**: W5 에는 `scenes` 개념이 자체가 없다.
장면 분할과 `what`/`mood` 는 원래부터 W7 출력이고, W7 은 **컷보다 먼저** 장면을
쓴다(작업 순서 1번). 즉 W7 안에 이미 "설계 단계"가 있다.

경고로만 남기는 것 둘 (`tone_warnings`) — 위반이 아니라 대개 놓친 자리다:
- 개그 장면인데 컷이 전부 `normal`
- 한 화의 장면 `tone` 이 전부 같음

### 8단계 — 컷이 확정된 뒤에 글자만 다시 쓴다 (W8)

실측한 1화는 이랬다:

    컷3  시하 "여기 앉으려고?"
    컷4  윤재 "커피 마실래요?"

둘은 대화가 아니다. 각자 자기 컷에 어울리는 말을 한 것이다. 그리고 12컷 중
10컷이 무음이라, 그림만으로 "3교시 끝, 40분 공강, 시하는 윤재를 피하고 싶다"를
전달해야 했다 — 안 된다.

**7단계가 화 전체를 못 봐서가 아니다.** 7단계는 원래부터 한 번의 호출로 컷을
전부 낸다. 문제는 컷을 하나씩 쓰면서 그 컷에 어울리는 말을 붙인다는 것이고,
그러면 말이 그림의 **설명**이 된다. 그래서 글자만 놓고 처음부터 다시 쓰는
단계를 뒤에 붙였다.

| 나눈 이유 | |
| --- | --- |
| 말이 서로를 받는다 | 글자만 놓고 다시 쓰면 컷4가 컷3을 받는다 |
| 재시도 예산이 안 섞인다 | 대사가 어색해서 되돌리면 카메라 분포·리듬까지 같이 다시 뽑혔다 |
| 그림을 다시 안 뽑고 대사를 고친다 | **글자가 이미지에 구워지지 않을 때만** 성립한다 (`scene.lettering: overlay`) |

**7단계도 글자를 계속 쓴다.** 8단계가 전부 다시 쓰는데 왜 두 번 쓰나 — 7단계의
초안은 **그림과 묶여 있는** 글자라서, 8단계에게 "이 컷에서 무슨 말이 오갈 자리인가"의
출발점이 된다. 백지에서 시작하면 8단계가 그림과 무관한 대사를 쓴다. 7단계에서
글자를 아예 빼는 쪽이 더 깨끗하지만, `gate_dialogue`·`text_warnings`·
`prose_warnings` 가 전부 그 자리에 걸려 있어 한꺼번에 옮기는 것은 위험하다.

**바꿀 수 있는 것과 없는 것**

| 바꾼다 | `speaker` `dialogue` `narration` `thought` `sfx` `screen_text` `bubble_zone` |
| --- | --- |
| **못 바꾼다** | `description` `shot` `angle` `size` `beat` `zone` `characters_in_frame` `composition` `render_style` |

글자를 **새로 넣어도 되고 빼도 된다** — 무음이던 컷을 채우는 것이 이 단계가 하는
일의 절반이다. `apply_text_patch` 는 적힌 컷만 바꾸고, **빠진 컷은 7단계의 글자를
그대로 둔다** — 조용히 지우면 모델의 실수 하나가 화의 일부를 통째로 무음으로 만든다.

**막히면 중단하지 않는다.** 8단계가 재시도를 다 쓰면 경고만 남기고 7단계의 글자로
간다. 여기서 세우면 이미 통과한 컷 한 벌이 통째로 버려지는데, 8단계가 실패해도
화는 성립하기 때문이다.

#### 8.5단계 게이트 — 전부 필드 대조다

"대사가 자연스러운가" 는 안 본다. 그건 사람이 읽어야 알고, LLM 판정을 넣으면
비용과 흔들림이 같이 들어온다. 막는 것은 **지키지 않으면 이야기가 망가지는 것**뿐이다.

| 검사 | 왜 |
| --- | --- |
| 대사에 세계관 낱말(`기록`·`평판`·`규정`·`낙인` …) | 인물이 설정을 소리 내어 말하면 독자에게 하는 설명이 된다. 같은 낱말이 나레이션·화면 글자에 있는 것은 **괜찮다** — 거기가 세계를 알려 주는 통로다 |
| **POV 가 아닌 인물의 속마음** | 취향이 아니라 **질문 장부를 지키는 장치**다. "저 사람은 왜 저러는가"가 열려 있는데 그 사람의 머릿속을 보여 주면 그 질문이 그 자리에서 닫힌다 |
| 속마음의 화자가 화면에 없음 | 화면에 없는 사람의 머릿속은 말풍선을 붙일 데가 없다 — 나레이션으로 옮긴다 |

경고로만 남기는 것: 무음 4연속 이상, 장면 첫 컷에 말이 없음.

POV 는 엔진 카드의 `[주인공]`이다(`pov_of`). 화마다 바꾸는 자리는 만들지 않았다 —
POV 가 흔들리는 것은 연출이 아니라 대개 사고다.

#### 나레이션은 자리가 절반이다

같은 문장이라도 어디에 놓이냐로 뜻이 달라진다. w8.txt 가 이걸 못박는다:

- **장면이 시작되는 컷** — 시간·장소·상황만. 구체적으로. ("3교시 끝. 다음 강의까지 40분.")
- **화가 끝나는 컷** — 뜻을 남긴다. ("적힌 것은, 언제나 사람보다 먼저 도착한다.")

경구를 첫 컷에 두면 아무 일도 안 일어난 자리에서 추상적인 문장이 나와 독자는
무슨 소린지 모른다. 같은 문장이 마지막 컷에 있으면 그때 꽂힌다.

### 그림 하네스까지 연결되어 있는가 (필드별)

콘티가 정한 것이 실제 그림에 닿지 않으면 없는 것과 같다. 한동안 실제로 그랬다 —
카메라 세 축과 장면 mood 를 만들어 놓고 webtoon-harness 는 그 필드를 읽지 않아,
연출이 하네스 경계에서 통째로 증발했다. 지금은 전부 연결되어 있다.

| 컷/화 필드 | 그림 쪽에서 무엇이 되는가 |
| --- | --- |
| `description` | scene_gen 이 패널 영어 서술로 옮긴다 |
| `dialogue` `narration` `thought` `sfx` | `bubble_clause` · `sfx_clause` 가 말풍선·상자·레터링으로 |
| `size` | Scene 레이아웃(칸 비율) |
| `beat` | `treatment_clause` — 집중선·빛번짐 같은 화면 보정 |
| `gaze` | scene_gen 규칙 3.5 — 패널의 시선 방향 |
| `render_style` | `panel_render` 문구 (normal/sd/emphasis **+ bleed/breakout**) |
| `shot` `angle` | `SHOT_EN`/`ANGLE_EN` 로 영어 샷 용어가 되어 패널마다 박힌다 (규칙 3.6) |
| `speaker` | 말풍선 꼬리를 누구에게 붙일지 (`bubble_clause`) |
| `scenes[].what` `.mood` | **scene_gen 규칙 3.4** — 그 장면 패널 전체의 공기 |
| `scenes[].tone` | 그림 쪽으로는 안 넘어간다 — 이 값의 일은 **7단계 안에서** 끝난다 (그 장면 컷들의 `render_style` 을 좌우) |
| `setting` place/time/weather/light | `staging_text` — 화 내내 고정되는 무대 |
| `zone` | 묶인 컷이 전부 같은 zone 이면(`scenegen.scene_zone`) 그 존의 배경 자산을 레퍼런스로 첨부 (`--zonesheet` 로 만든 것이 있을 때만) |
| `characters_in_frame` | 컷마다 누가 화면에 있는가 — 시트를 붙일지 말지의 근거 (예전에는 서술에서 이름을 찾았다) |
| `composition` `composition_note` | `composition_clause` — 오버숄더·프레임인프레임 같은 구도를 영어 지시로 |
| `screen_text` | `screen_ui_clause` — 화면을 **비워** 그리게 하고 글자는 합성 |
| `bubble_zone` | `bubble_zone_clause`(그 자리를 비우라는 지시) + `bubbles.auto_regions`(합성 자리 초안) |

`transition` 만 넘기지 않는다. 컷 **사이**의 관계라서 패널 안에 그릴 것이 없다 —
그 효과는 이미 `gap_after`(여백)와 Scene 분할로 반영되어 있다.

> **`scenes[].mood` 가 이 연결의 핵심이다.** 컷 서술은 "무엇이 보이는가" 만 말한다.
> "어떤 공기로 그릴 것인가" 는 mood 에만 있고, 이게 안 넘어가면 그림 쪽 LLM 이
> 패널마다 톤을 새로 정한다 — 같은 장면인데 한 컷은 서정적이고 다음 컷은
> 스릴러가 된다. `scene_gen.txt` 규칙 3.4 가 "설명과 분위기 중 한 문장을 골라야
> 하면 분위기에 써라" 라고 못 박는다.

> ⚠️ **`shot` 을 필드로 뺀 것과 규칙 2 는 한 몸이다.** 예전 `scene_gen.txt` 규칙 2 는
> 샷을 *"the shot signalled by the Korean text"* 로 **서술에서 짐작**했다. 콘티가
> 서술에서 카메라 낱말을 빼내 필드로 옮겼으므로, 필드를 안 읽으면 샷 신호가
> 아예 사라진다. 둘은 같이 바뀌어야 한다 (규칙 2 → 3.6 참조로 고쳤다).

기존 run 은 이 필드들이 없어도 그대로 로드된다 — `storyload` 가 빈 값으로 읽고,
`--build-view` 는 카메라 칸에 `—` 를 찍는다. 실제 run 두 개(신·구)로 확인했다.

측정(gpt-4.1, 10~17화 101컷, build 를 허용하기 전): normal 68 · emphasis 19 · sd 14
(화당 평균 1.75컷). SD 는 전부 release/hold 에 붙었고 스팅어에는 하나도 없었다.

### 7단계 컷 서술 — 소설 지문이 아니라 그림 한 장의 설명서

컷은 이미지 한 장으로 그려진다. 소설 지문처럼 쓰면 그릴 수 없는 것이 나온다.
초기 출력이 그랬다 — "윤아가 고개를 숙인 채 호스를 닦다가, 시선을 느끼고 몸을 웅크린다"
는 **두 개의 순간**이다. 한 장으로 그리면 둘 다 뭉개진다.

| 규칙 | 내용 |
| --- | --- |
| 한 컷 = 한 순간 | 동작이 둘이면 컷을 나눈다. `~다가` `~하고 나서` `~한 뒤` 금지. `~하고 있다` 정지 상태로 |
| 카메라는 쓰지 않는다 | 거리·앵글·크기는 전부 필드다. 서술에 다시 적으면 같은 지시가 두 번 들어간다 |
| 보이는 것만 | 속마음·내레이션 금지. 감정은 표정·자세·시선·손의 위치로 |
| 인물 없는 컷 허용 | 배경만, 사물만, 손만 나오는 컷도 연출이다 (`shot: 인서트`). 게이트가 최소 1개를 요구한다 |
| 대사 없는 컷 허용 | 침묵도 카드다. 한 화에 최소 2개 — **다만 기본값이 아니다.** 상한은 `gate_text` 가 잡는다 (말 있는 컷 50% 이상, 말 없는 컷 2연속까지) |

**카메라는 `size` 가 아니다.** `size` 는 컷이 화면에서 차지하는 비율이고 `shot` 은 그 안에서
무엇을 얼마나 가까이 보는가다. 처음에는 이 구분을 안 적었더니 모델이 카메라 자리에
`wide,` `tall,` 처럼 size 값을 그대로 적었고(12컷 중 4컷), 구분을 적어 넣은 뒤에도
완성된 run 에서 49~100%가 그랬다. 말로 고쳐지지 않아 필드로 분리했다 — 위 표를 볼 것.

이 다섯 가지는 **경고만 하고 반려하지 않는다.** 걸리는 것은 "틀린 것"이 아니라 "웹툰
문법에서 벗어난 것"이고 장르에 따라 예외가 있다. 반려하면 컷 내용 전체를 다시 뽑게
되는데 그 비용이 경고 한 줄보다 훨씬 크다. 사람이 보고 판단할 몫으로 남긴다.
경고는 로그에 `서술 경고:` 로 찍히고 `ep{MM}_cuts.json` 의 `_notes` 에 남는다.

`~한 뒤` 를 잡는 정규식은 종성이 ㄴ 인 한글 음절 399개를 만들어 쓴다("울린"의 ㄴ 은
음절 안에 합쳐져 있어 `[ㄴ]` 로는 잡히지 않는다). 공간을 뜻하는 `뒤에서`·`뒤로`·`뒤편`과
한 글자 낱말 뒤의 `뒤`("문 뒤에")는 뺀다 — 틀린 경고가 쌓이면 전부 안 읽게 되므로
놓치는 쪽을 택했다.

### 모델이 판단할 것과 코드가 계산할 것 (7단계)

처음에는 다섯 필드를 전부 모델이 쓰고 게이트 여덟 개로 검사했다. 실패했다. gpt-4.1 이
**여섯 번 연속 같은 자리에서** 걸렸다 — 가운데가 전부 `build` 이고 Scene 이 6~9컷이 되는
실패였다. 조건들이 서로 얽혀 있어서 하나를 고치면 다른 하나가 깨졌다. 화당 3~4회 재생성이
필요했고, 그러고도 여백은 12컷 중 10컷이 `1` 이었다.

5단계의 유령 id 와 같은 문제다. **온도 0.9 에서 얽힌 제약을 자연어로 맞추게 하면 안 된다.**
그래서 나눴다.

  - **모델** : `description` `dialogue` `shot` `angle` `transition` `size` `beat`
    `render_style` — 내용을 봐야 알 수 있는 판단
  - **코드** : `gap_after` `scene_break` `gaze` — 위 시퀀스에서 나오는 산수

여백 계산 규칙은 이렇다. **다음 컷이 turn 이거나 통컷(bleed) → `3`**(터지기 직전의
뜸들이기), 다음 컷의 전환이 `장면` → `2`(시간·장소가 건너뛴다), 현재가 release → `0`
(몰아침), 다음 컷의 전환이 `순간` → `0`(같은 동작의 다음 찰나), 다음 컷의 전환이
`분위기` → `2`(시간이 안 흐르는 컷은 머무르게 둔다), 현재가 hold → `2`, 나머지 → `1`.
반전이 셋 이상이면 나머지는 `2` 로 낮춘다(`3` 은 화당 2회까지).
이러면 "반전 직전 여백 2 이상"과 "여백이 3종 이상 흩어지고 0 과 3 이 각각 최소 1개"가
**구조적으로 항상 만족된다.** 게이트로 강제할 일이 아니라 계산하면 되는 것이었다.

처음에는 `beat` 만 보고 계산했는데, 그러면 여백이 리듬 라벨의 함수일 뿐 **컷 사이에
실제로 무슨 일이 일어났는지와 무관**해진다 — 장면이 통째로 바뀌는 자리와 같은 동작이
이어지는 자리에 같은 여백이 들어갔다. 여백은 "두 컷 사이에 흐른 시간"이므로 전환
유형이 1차 근거다. `transition` 축이 생기면서 그 근거가 데이터로 들어왔다.

화면 경계도 같다. `hold` 나 `turn` 으로 끝나는 자리 중에서 한 화면이 2~5컷이 되도록
코드가 고른다. 시선은 마지막 컷만 `at-viewer`(스크롤을 멈춘다), `인서트` 컷은 시선을
줄 사람이 없으므로 `down`, 나머지는 거리·앵글에 따라 `down` 또는 `toward-next` 다.

남은 게이트는 모델 판단 영역뿐이다 — turn 최소 1개, impact 최대 2개, 같은 beat 4연속 금지,
같은 size 4연속 금지, 마지막 컷 size/beat. 전부 단순 카운팅이다.

**모델에게 남는 책임은 `beat` 를 정직하게 다는 것 하나다.** 멈추는 자리를 `hold` 로 달지
않으면 코드가 화면을 끊을 자리를 찾지 못한다. 그래서 프롬프트는 "컷 N개면 hold 와 turn 을
합쳐 최소 N÷5개"라는 산수를 명시한다. 그래도 모자라면 코드가 가장 덜 나쁜 자리에서 끊고
`연출 메모:` 로 경고를 남긴다 — 조용히 잘라내지 않는다.

계산 결과는 `layout_violations()` 가 다시 검사한다. 게이트가 아니라 assert 다. 여기서
뭐가 나오면 모델이 아니라 `derive_layout()` 의 버그다.

측정 결과(gpt-4.1, 서윤아 1~4화):

| | 나누기 전 | 나눈 뒤 |
| --- | --- | --- |
| 화당 호출 | 3~4회 | 1~2회 (4화 중 3화가 1회) |
| 1화 토큰 | 73,418 | 30,614 |
| 여백 분포 (48컷) | 대부분 1 | 0이 7 · 1이 25 · 2가 5 · 3이 7 |
| 크기 분포 (48컷) | — | wide 8 · normal 22 · tall 12 · impact 6 |

**왜 7.5단계가 아닌가.** 이전 판에는 연출만 붙이는 7.5단계가 따로 있었다. 확정된 컷 목록에
`beat`/`gap_after`/`gaze`/`scene_break` 를 얹고 컷은 한 글자도 고치지 않았다. 문제는 그
시점에 앞 단계가 이미 균일한 컷 10개를 써 놓았다는 것이다. 사후에 라벨을 무엇으로 붙이든
결과는 "크기 같은 이미지 나열"이었다. impact 컷에 설명을 욱여넣으면 둘 다 죽으므로 크기와
내용은 같은 호출에서 정해야 한다. 그래서 7.5단계를 7단계로 흡수했고 `ep{MM}_direction.json`
도 없앴다. 컷 파일 하나에 전부 들어간다.

```
python webtoon.py --run <run_id> --cuts-only               # 회차는 그대로, 컷만 다시 뽑기
python webtoon.py --run <run_id> --cuts-only --episode 1   # 특정 화만
```

`--cuts-only` 는 4~6단계를 다시 돌지 않고 같은 회차 설계에 컷 분해만 바꿔 보려고 있다.

### 5단계 — 무대는 여기서 정한다 (컷 단조로움의 상류 원인)

컷이 얼굴 나열이 되는 원인을 7단계에서만 찾다가 상류를 놓쳤다. 실제로 나온 1화
요약을 보면 답이 나와 있다.

> 시하는 K대 캠퍼스에서 매일처럼 여유로운 표정으로 친구들과 이야기를 나누다가,
> … 시하는 순간적으로 **눈매가 단단히 날카로워지고 턱이 굳어진다.** …
> 수업이 끝난 뒤, 학과 단톡방에 사진과 목격담이 올라가고 …

장소는 잔디광장과 복도 둘, 물리적 사건은 거의 없고, 전부 대화와 표정이다. 게다가
요약 안에 **표정 묘사가 이미 들어 있어서** 7단계가 그 문장을 그대로 옮겨 적는다.
스팅어에는 `"…윤재의 시선이 클로즈업된다"` 처럼 카메라까지 지정되어 있었다.

파이프라인 전체를 훑어보니 공간 어휘가 어디에도 없었다.

| 자리 | 인물 재료 | 공간 재료 |
| --- | --- | --- |
| 엔진 카드 | 외형 4줄 · 표정 6종 · 색 6개 | 장소 한 줄(`서울 K대`), 시간대·소품 없음 |
| `p1.txt` | 상세 | `소품`은 **명시적으로 제외**(시트에는 맞는 설계) |
| `p2.txt` / `w4.txt` / `w6.txt` | — | 공간 어휘 0회 |
| `w5.txt` summary 스펙 | — | "이 화에서 벌어지는 사건. 구체적으로." 뿐 |

어휘 자산이 얼굴에만 있으니 카메라가 얼굴로 돌아오는 것은 당연했다. 7단계에
앵글·전환 어휘를 아무리 늘려도 **가리킬 대상이 없으면** 소용이 없다.

그래서 5단계가 회차마다 `setting` 을 함께 낸다.

| 칸 | 무엇 | 7단계에서 무엇이 되는가 |
| --- | --- | --- |
| `place` | 건물이 아니라 그 안의 자리 | 원경 컷, 공간의 기준 |
| `time` | 시간대·날씨 = 빛 | 같은 장소를 다른 그림으로 만드는 가장 싼 변주 |
| `props` | 화면에 보이는 사물 2~4개 | **인서트 컷의 재료** |
| `movement` | 어디서 어디로 | 거리 변화(원경→전신→바스트)의 근거 |

`gate_setting` 이 네 칸을 검사하고, 7단계 프롬프트에는 `setting_block` 으로 회차
JSON 과 **따로** 실린다 — 회차 JSON 안에 묻혀 있으면 모델이 서사 재료로만 읽고
넘어간다. 무대는 서사가 아니라 그릴 대상 목록이다.

장소는 `series.json` 의 `places` 에 쌓여 다음 화 프롬프트에 보인다. 매 화 새 장소를
만들면 세계가 넓어지는 게 아니라 얇아지기 때문이다 — 같은 공간에 두 번째로 가야
독자가 그곳을 기억하고, 그때 달라진 것이 보인다.

`w5.txt` 에는 금지도 함께 넣었다. **요약과 스팅어에 표정·속마음·카메라를 쓰지 않는다.**
감정은 "인물이 무엇을 하는가"로 쓴다 — 그래야 7단계가 그 행동을 어느 거리에서 어떻게
볼지 고를 수 있다.

### 5단계 — id 는 모델이 짓지 않는다

5단계는 온도 0.9 생성 단계다. 여기서 id 정합성을 자연어 지시로 맞추려는 시도는
반복해서 실패했다. 엔진급 질문을 상환 대상으로 지목하고, 출력 예시의 `Q-3` 를 그대로
베끼고, 닫을 게 없으면 빈 문자열을 넣고, 같은 화에서 연 `temp_id` 를 닫으려다 여는
쪽과 닫는 쪽 id 가 어긋났다. 프롬프트를 다섯 번 고쳐도 같은 종류가 재발했다.

그래서 **5단계 산출물에는 id 가 아예 없다.** 모델은 본문만 쓰고, 나머지는 코드가 붙인다
(`assign_ids`).

| 항목 | 모델이 쓰는 것 | 코드가 하는 것 |
| --- | --- | --- |
| 화 번호 | (없음) | `episodes` 배열 순서대로 `order` 1부터 부여 |
| 여는 질문 | 질문 본문 + 유형 | `temp_id` 를 `T{화}-{순번}` 으로 부여 |
| 상환 | 닫는 질문의 **본문** (`question_text`) | 장부의 열린 질문과 본문을 맞춰 `ledger_id` 연결 |
| 스팅어 | 연결될 질문의 **본문** (`linked_question_text`) | 같은 방식으로 `linked_question_id` 연결 |

본문 매칭은 정규화 후 유사도 0.6 이상일 때만 성립한다(`match_question`). 못 맞추면:

- **상환** — 그 상환만 조용히 버린다. **재생성 사유가 아니다.** 엉뚱한 질문을 닫는 것보다
  무시하는 편이 낫다. 버린 내역은 실행 로그에 남는다.
- **스팅어** — 그 화가 연 첫 질문으로 잇는다. 실패시키지 않는다.
- 엔진급 질문을 지목한 상환도 같은 자리에서 버려진다. 장부는 훼손되지 않는다.

같은 Arc 의 앞선 화가 연 질문도 상환 대상이 된다. 장부 id 는 6단계 통과 후에 발급되므로
그때까지는 임시 id 로 들고 있다가 `commit_ledger` 에서 실제 id 로 바뀐다.

**상환 강제는 Arc 단위다.** Arc 진입 시점 장부에 열린 질문이 1개 이상 있는데 그 Arc 의
어느 화도 상환하지 않았을 때만 되돌린다. 화 단위 강제는 없앴다 — 매 화 억지로 닫으려다
없는 id 를 지어내는 것이 실패의 주된 경로였기 때문이다.

6단계에는 코드가 붙인 id 가 들어간 산출물이 그대로 전달된다. 검사 AI 는 그 값을 옮겨
적기만 하고, 옮겨 적다 틀려도 코드가 본문으로 다시 맞춘다. 그래도 못 맞추면 그 상환만
반영되지 않는다 — **검사자가 인정한 것만 장부에 들어간다**는 규칙은 그대로다.

**6단계는 별도 세션이다.** 생성 히스토리를 넣지 않고, 검사 AI가 인정한 것만
(`verified_question_types` / `verified_closures`) 질문 장부에 들어간다.
작가가 신고한 유형이 아니라 검사자가 판정한 유형이 기록된다.

`eq_untouched` 위반(엔진급 질문이 닫힘)은 **자동 재생성하지 않는다.** 즉시 중단하고
사람을 부른다. 그 외 불합격 화는 해당 Arc 를 5단계로 되돌려 재생성한다(최대 2회).

### 질문 장부와 자동 경고

| 신호 | 조건 |
| --- | --- |
| 미스터리 박스 | 최근 3화 상환 0건 |
| 떡밥 과부하 | 안 풀린 질문이 상한 초과 (기본 5, `--ledger-cap`) |

`prompts/` 안의 텍스트 파일이 원문이다. 코드는 `{변수명}` 만 치환하고 나머지 중괄호는

유형 **하나만** 고친다.

## 4. 온도 주의

이 실험은 창작 0.9 / 심사 0.2 의 대비에 기대고 있다. 그런데 추론 계열 모델은
`temperature` 를 아예 받지 않는다.

| 프로바이더 | 온도를 못 받는 계열 | 권장 |
| --- | --- | --- |
| Gemini | 없음 (추론 모델도 받는다) | `gemini-2.5-flash` |
| OpenAI | `o1` `o3` `o4` `gpt-5` | `gpt-4.1` |
| Anthropic | Opus 5 / 4.8 / 4.7, Sonnet 5, Fable 5 | `claude-opus-4-6` |

해당 모델을 고르면 실행 전에 경고가 뜨고, `meta.json` 에
`temperature_applied: false` 로 남는다. 그래도 보내려면 `.env` 에
`FORCE_TEMPERATURE=1`.

OpenAI 는 프롬프트에 `json` 이라는 낱말이 들어 있을 때만 JSON 모드를 켠다
(`OPENAI_JSON_MODE=1`, 기본 켜짐). 낱말이 없으면 API 가 거부하므로 코드가 알아서
끈다. Gemini 도 `GEMINI_JSON_MODE=1` 로 같은 규칙을 따른다
(`response_mime_type: application/json`).

**Gemini 의 사고 토큰 주의.** Gemini 는 기본으로 '사고'를 하고, 그 토큰이
`MAX_TOKENS` 를 갉아먹어 본문이 빈 채로 끊길 수 있다. 그래서 기본값은
`GEMINI_THINKING=off` 다. `auto` 는 모델 기본값에 맡긴다.

세대마다 파라미터 이름이 다르다 — **3.x 는 `thinking_level`**(`minimal` `low`
`medium` `high`), **2.x 는 `thinking_budget`**(토큰 수). 서로의 값을 그대로
보내면 `400 INVALID_ARGUMENT` 가 난다. `GEMINI_THINKING` 에 무엇을 적든 코드가
모델 이름을 보고 맞는 쪽으로 번역하므로, 보통은 `off` 로 두면 된다.

**모델 이름 주의.** `gemini-2.5-flash` 는 목록에는 보이지만 신규 키로는
호출되지 않는다(`404 no longer available to new users`). 확인된 것은
`gemini-3.5-flash` · `gemini-3.6-flash` · `gemini-3.1-pro-preview` 다.
`gemini-flash-latest` 도 되지만, 재현성을 위해 버전을 박아 쓰는 쪽을 권한다.

### 원문 대비 손댄 곳 (전부 의도적)

- `p2.txt`: `forbidden_subversion` 항목을 추가했다. 게이트 요건인데 문서 10-2 출력
  스키마에 없었다.
- `p3.txt`: `capture_sentence` 와 `target_stage` 를 추가했다. 판정 도출 규칙표와
  재실행 라우팅을 코드가 계산하려면 필요하다.
- `scene.txt`: 장면 개수를 `{scene_count}` 로 뺐다 (원문은 "3~4개" 고정).
- `control.txt`: JSON 출력 형식 한 줄만 붙였다. 대조군의 순진함은 그대로 뒀다 —
  여기에 품질 지시를 넣으면 비교가 무의미해진다.
- `engine_card`: `[금지된 뒤집기]` 블록을 넣었다.
- `w4.txt`: 손대지 않았다.
- `w7.txt`: 완주한 실행을 세어 보고 크게 고쳤다 (위 알려진 구멍 7·8번).
  - 카메라를 서술 첫머리의 낱말에서 **필드 세 개**(`shot` `angle` `transition`)로
    분리했다. 서술에는 카메라·크기 낱말을 못 쓰게 했다.
  - `render_style` 에 `bleed`(통컷) · `breakout`(칸 밖으로)을 더했다.
  - 작업 순서에 `shot_sequence` · `angle_sequence` 를 추가해 **컷 서술보다 먼저**
    카메라를 확정하게 했다.
  - 5-5 절(말의 밀도)과 5-7 절(상황을 세우는 수단 넷)을 새로 썼다. "글자 없는 컷을
    넣어라 / hold 컷은 대개 침묵이다" 처럼 무성 쪽으로만 밀던 문구를 걷어냈다.
  - `speaker` 를 출력 스키마에 추가했다.
  - 대화씬 절(좌우 고정 · 시선 · 어깨 너머 · 대사 사이 인서트)을 새로 넣었다.
- `w5.txt`: `setting`(장소·시간대·사물·동선)을 출력 스키마에 추가하고, summary 와
  stinger 에 **표정·속마음·카메라를 쓰지 못하게** 했다. 요약에 "눈매가 날카로워지고
  턱이 굳어진다" 가 들어가면 7단계가 그대로 옮겨 적어 얼굴 컷이 된다.
  그 밖에 출력 스키마에서 `order` `temp_id` `ledger_id` `linked_question_id` 를
  전부 뺐다. 대신 `question_text` `linked_question_text` 로 본문을 쓰게 하고,
  상환 강제를 "매 화"에서 "Arc 안에서 최소 한 화"로 바꿨다. 화 수를
  `{episode_count}` 로 못 박았다 — 재생성 지시를 받으면 불합격 화만 남기고
  나머지를 버리는 일이 실제로 있었다.
