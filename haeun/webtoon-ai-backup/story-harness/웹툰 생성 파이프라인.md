# Lore 웹툰 생성 파이프라인 명세서

| 항목 | 내용 |
| --- | --- |
| 목적 | 재미가 확인된 스토리를 **연재 가능한 웹툰 형식**(큰 줄거리 → 회차 → 컷)으로 옮긴다 |
| 앞 문서 | 「Lore 스토리 파이프라인 명세서」 — 캐릭터·프리미스·구조 검수·1화 장면·사람 판정 |
| 독자 | 개발자 · PM · PO · 기획 · 멘토 |
| 구성 | 1~7장 = 무엇을 왜 만드는가 / 8장 = 프롬프트 전문 |

---

## 1. 두 파이프라인의 관계

파이프라인은 두 덩어리다. 묻는 질문이 다르므로 화면도 판정도 분리한다.

| | 스토리 파이프라인 | **웹툰 파이프라인 (이 문서)** |
| --- | --- | --- |
| 질문 | 이 이야기 재미있는가? | 그 이야기를 웹툰 형식으로 잘 옮겼는가? |
| 단계 | 주인공 → 설정 → 구조 검수 → 1화 장면 | 큰 줄거리 → 회차 → 회차 검사 → 컷 |
| 판정 | 사람이 장면을 읽고 "다음이 궁금한가" | 코드 게이트가 규칙 위반을 잡는다 |
| 실패 시 | 프리미스를 다시 뽑는다 | 그 단계만 다시 만든다 (최대 2회) |
| 화면 | 「이야기」 | 「웹툰」 |

**순서를 지켜야 한다.** 재미없는 설계로 컷을 아무리 잘 뽑아도 재미없는 웹툰이 나온다. 그래서 웹툰 파이프라인은 자동으로 이어지지 않는다 — 사람이 「웹툰」 화면에서 [웹툰으로 만들기]를 눌러야 시작한다.

### 접점 — 작품 카드

두 파이프라인을 잇는 것은 **작품 카드(엔진 카드)** 하나다. 코드가 조립하며, 4~7단계 모든 프롬프트에 원문 그대로 삽입된다.

```
=== 엔진 카드 ===
로그라인 · 장르 기대 / 장르 배신
[RULE] 법칙 · 재발동 조건
[COST] 대가 · 발동 메커니즘
[IRONY] 충돌 · 양측 욕망 · 출구 봉쇄 이유
[낙차] · [엔진급 질문]
[주인공] 이름 · want · need · 겉모습 · 속모습
[작가가 처음 준 한 줄]          ← 원문 그대로
[1화 도입부 — 사람이 통과시킨 장면]  ← 한 줄 압축 + 그 장면의 선택
```

마지막 두 블록이 핵심이다. 카드에 로그라인·룰·대가만 담으면 작가가 쓴 구체적 묘사(생김새, 그 세계에만 있는 것)와 사람이 통과시킨 장면이 여기서 잘려 나간다. 그러면 회차·컷 단계는 "미지의 무언가"만 받게 되고, 빈칸을 학습 데이터 평균값(의문의 책·빛나는 유물·정체불명의 기호)으로 채운다. **장면 단계에서 이미 겪은 실패가 뒤에서 그대로 재발한다.**

카드는 [웹툰으로 만들기]를 누를 때 다시 조립된다. 장면이 그때는 이미 나와 있으므로, 사람이 통과시킨 도입부가 회차 설계의 출발점이 된다.

## 2. 전체 구조

```
[스토리 파이프라인 완료 — 장면까지 나오고 사람이 판정함]
        │
        ▼  사람이 [웹툰으로 만들기]를 누른다
   작품 카드 재조립 (작가 원문 + 통과한 장면 포함)
        │
4단계  큰 줄거리 분할        Arc 4~6개, 각 2~5화
        │   게이트: 설정 3종 사용 · 반전 Arc 비율 1/3 이상
5단계  Arc → 회차 분해       Arc 하나씩 반복
        │   게이트: 질문 유형 배분 · 매 화 상환 · 떡밥 총량
6단계  회차 검사 (별도 세션)  화별 7체크, 불합격 화만 5단계 재생성
        │   치명: 엔진급 질문 훼손 → 자동 재생성 금지, 사람 호출
7단계  회차 → 컷 분해        회차 하나씩 반복, 컷 8~16개
        │   게이트: 엔진 컷 분산 · 마지막 컷이 스팅어 · 독자 우위 컷
      완료
```

4~7단계는 **Arc 단위·회차 단위로 반복**된다. Arc가 4개면 5·6단계는 4번, 7단계는 회차 수만큼 돈다. 실제 호출 수는 대략 `1 + 4 + 4 + 12 = 21회` 안팎이다.

## 3. 각 단계가 하는 일

### 4단계 — 큰 줄거리 분할

작품 카드와 캐릭터 시트를 받아 Arc 4~6개로 나눈다. 각 Arc는 2~5화 분량이다.

- 각 Arc는 엔진 요소(rule/cost/irony) 중 하나를 **주 동력**으로 쓴다. 전체를 합쳤을 때 셋이 모두 최소 한 번은 주 동력이어야 한다. 한 요소만 반복하면 나머지는 장식이 된다.
- Arc 종류는 전개 · 반전 · 상승 · 해소 넷이며, **반전 비율이 1/3 이상**이어야 한다. 기대배신은 Arc 스케일에서도 재생산되어야 하고, 전개·상승만 이어지면 설정집 비대증에 빠진다.
- 각 Arc가 여는 질문(opens)과 닫는 질문(closes)을 문장으로 적는다. 엔진급 질문은 어느 Arc에서도 닫지 않는다.
- 순차 반전 Arc는 그 반전이 배신할 전제를 **앞 Arc가 실제로 심어야** 한다. 앞에서 심지 않은 걸 뒤에서 뒤집으면 반전이 아니라 설정 변경이다.

**코드 게이트:** rule·cost·irony 각 1개 이상 사용 / 반전 비율 ≥ 1/3 / order 1부터 연속 / 화 수 2~5.

### 5단계 — Arc를 회차로 분해

Arc 하나를 화 단위로 쪼갠다. 이 단계가 연재 리듬을 결정한다.

**질문 3유형.** 독자를 붙잡는 장치는 셋인데 만드는 방식이 정반대다.

| 유형 | 만드는 법 | 지속 |
| --- | --- | --- |
| mystery (왜?) | 정보를 **숨긴다** | 공개되는 순간 소멸 |
| suspense (어떻게 되지?) | 정보를 **준다**, 결과만 남긴다 | 결과가 나올 때까지 |
| dramatic_irony (안 돼, 저러다…) | 독자에게**만** 준다 | 캐릭터가 알 때까지 |

"질문이 생기게 하라"는 지시를 받으면 모델은 가장 비용이 싼 경로인 정보 은닉으로 간다. 그래서 **신규 질문의 절반 이상이 suspense·dramatic_irony**여야 하고, mystery는 화당 최대 1개다.

**부채 규칙.** 질문 = 부채, 답 = 상환, 상환 이력 = 신용.

1. 엔진급 질문은 절대 닫지 않는다
2. **매 화 최소 하나를 닫는다** (예외 없음)
3. 닫는 답이 새 질문을 파생시키면 최상
4. 답 자체가 또 하나의 기대배신인 상환(is_betrayal)이 Arc에 최소 하나
5. 열자마자 전부 닫으면 다음 화를 누를 이유가 사라진다

**화 설계.** 각 화는 어떤 엔진 요소가 발동하는지(engine_fired)를 밝힌다. 빈 배열은 허용하지 않는다 — 엔진이 발동하지 않는 화는 존재 이유가 없다. 마지막 컷의 훅(스팅어)은 반드시 열린 질문 하나와 연결된다.

### 6단계 — 회차 검사 (별도 세션)

**생성 히스토리 없이 새 컨텍스트에서 실행한다.** 화별로 7개 항목을 보고 pass/fail을 매긴다. 위반 하나라도 있으면 fail이다.

| 체크 | 보는 것 |
| --- | --- |
| question_type_ratio | 정보를 줘서 만든 질문이 절반 이상인가. **작가 신고를 믿지 않고 본문을 읽고 직접 판정** |
| mystery_quota | 이 화의 신규 은닉형 질문이 2개 이상이면 위반 |
| debt_closed | 이 화에서 질문을 최소 하나 닫았는가. 장부에 없는 id를 가리키면 상환 불인정 |
| closure_is_betrayal | 상환이 전부 단순 정보 공개형이면 위반 |
| engine_fired | 적어놓은 엔진 요소가 요약 안에서 실제로 발동하는가 |
| stinger_linked | 스팅어가 실재하는 질문과 연결되는가 |
| **eq_untouched** | 엔진급 질문을 닫았는가 — **치명 위반** |

검사 결과는 두 가지로 쓰인다. 불합격 화는 그 화만 5단계로 되돌려 재생성하고(최대 2회), 검사 AI가 인정한 질문·상환만 질문 장부에 반영된다. **작가가 신고한 유형이 아니라 검사자가 판정한 유형이 장부에 들어간다.**

`eq_untouched` 위반은 자동 재생성하지 않는다. 이야기의 중심 질문이 닫혔다는 뜻이므로 실행을 즉시 멈추고 사람을 부른다.

### 7단계 — 회차를 컷으로

검사를 통과한 화 하나를 컷 8~16개로 분해한다.

- **엔진 발동 컷을 마지막 1/4에 몰아넣지 않는다.** 엔진이 끝에서만 작동하면 앞 3/4는 긴장 없는 소모 구간이 된다.
- **스팅어는 반드시 마지막 컷**이다.
- 이 화에 dramatic_irony 질문이 있으면 **독자만 알고 인물은 모르는 컷**을 최소 하나 넣는다. 이게 그 질문의 물리적 구현이며, 없으면 질문이 작동하지 않는다.
- 컷 서술은 **화면에 보이는 것만** 쓴다. 속마음·내레이션 금지. "슬퍼한다"가 아니라 무엇이 보이는지 쓴다.

## 4. 질문 장부

연재가 길어지면 떡밥이 자동으로 무너진다. 그래서 질문을 코드가 장부로 추적한다.

| 필드 | 내용 |
| --- | --- |
| id | Q-1, Q-2 … 검사 통과 후 코드가 발급 |
| text / type | 질문 본문 · 검사자가 판정한 유형 |
| openedAt / closedAt | 열린 위치 · 닫힌 위치 (Arc, 화) |
| plannedPayoffEpisode | 상환 예정 화 (통산 번호) |
| isEngine / isBetrayal | 엔진급인가 · 배신형 상환이었는가 |

**자동 경고**

| 신호 | 조건 | 뜻 |
| --- | --- | --- |
| 미스터리 박스 | 최근 3화 상환 0건 | 떡밥만 쌓이고 회수가 없다 |
| 떡밥 과부하 | 안 풀린 질문이 상한 초과 | 궁금한 게 너무 많아 아무것도 안 궁금해진다 |
| 연체 | 상환 예정 화를 2화 이상 넘김 | 고구마 구간 |
| 엔진급 훼손 | 엔진급 질문이 닫힘 | 치명 — 즉시 중단 |

떡밥 상한은 현재 코드가 8개, 기준 문서가 5개다. 작업기억이 동시에 추적할 수 있는 미해결 사안이 3~5개라는 근거를 따르면 5가 맞고, 지금 코드가 더 헐겁다.

## 5. 코드가 판정하는 것 / 모델이 판정하는 것

원칙은 스토리 파이프라인과 같다. **모델은 좁은 질문에만 답하고, 최종 판정은 코드가 계산한다.**

| 단계 | 모델이 하는 일 | 코드가 하는 일 |
| --- | --- | --- |
| 4 | Arc 설계 | 요소 사용·반전 비율·순번·화 수 검사 |
| 5 | 회차 설계 | (검사 전에는 판정하지 않음) |
| 6 | 화별 위반 지목 + 질문 유형 재판정 | 전체 pass 여부 · 유형 비율 계산 · 장부 반영 · 재생성 라우팅 |
| 7 | 컷 분해 | 엔진 컷 실재·분산, 스팅어 위치, 독자 우위 컷 존재 검사 |

## 6. 아직 이어지지 않은 곳

솔직하게 남긴다. 이 목록이 다음 작업의 순서다.

| # | 내용 | 영향 |
| --- | --- | --- |
| 1 | **장면과 1화의 관계가 느슨하다.** 작품 카드에 장면 요약이 실리지만, 5단계 프롬프트가 "1화는 이 장면에서 이어 쓰라"고 강제하지는 않는다 | 사람이 통과시킨 도입부와 실제 1화가 어긋날 수 있다 |
| 2 | **"사건은 선택에서 시작한다"가 5·7단계에 없다.** 장면 단계에만 있는 규칙이다 | 회차 요약에서 "의문의 물건 발견"류가 다시 나올 수 있다 |
| 3 | **단서 장부가 없다.** 반전을 쓸 때 앞 화에 단서 2개가 심겨 있는지 추적하지 않는다 | 사기 반전을 막을 방법이 없다 |
| 4 | **아크 장부가 없다.** 캐릭터 변화 비트가 발화하는지 추적하지 않는다 | 제자리걸음(사건은 반복되는데 인물이 그대로)을 못 잡는다 |
| 5 | **떡밥 상한이 8이다.** 기준 문서는 5 | 과부하 경고가 늦게 뜬다 |
| 6 | **질문 유형이 3종이다.** 기준 문서는 은닉형을 순수 은닉 / 조각 제공으로 나눈다 | 가장 위험한 순수 은닉형을 따로 세지 못한다 |
| 7 | **실제 모델로 검증한 적이 없다.** 4~7단계는 연습(Mock) 데이터로만 돌려봤다 | 이 단계 품질은 아직 아무도 모른다 |

7번이 지금 상태의 핵심이다. 코드와 프롬프트는 전부 있고 돌아가지만, **진짜 AI로 뽑은 회차·컷을 아무도 본 적이 없다.** 1~6번을 먼저 고치기보다 한 편을 실제로 돌려보고 무엇이 실제로 문제인지 확인하는 편이 낫다.

## 7. 화면에서 하는 일

**「웹툰」 탭**

1. 장면까지 나온 이야기만 목록에 올라온다 (스토리 단계를 끝낸 것)
2. [웹툰으로 만들기] → 작품 카드 재조립 → 큰 줄거리 → 회차 → 검사 → 컷 순서로 진행
3. 결과는 읽는 순서 그대로 — 큰 줄거리 · 회차(질문·마지막 장면) · 컷 표
4. 컷 표에서 파란 줄은 설정이 발동하는 컷, 노란 줄은 다음 화를 부르는 마지막 컷, 👁는 독자만 아는 정보
5. 아래 [AI를 부른 기록]에 단계·모델·시간·토큰·판정이 한 줄씩 쌓인다. 프롬프트 원문과 답변 원문은 「기록」 탭에서 펼쳐 본다

중간에 멈추는 경우는 둘이다. **확인 필요**(자동으로 정하면 안 되는 지점)와 **중단**(엔진급 질문 훼손 같은 치명 위반). 둘 다 화면에 이유가 뜨고, 처리한 뒤 [이어서 만들기]를 누르면 그 지점부터 계속된다.

## 8. 프롬프트 전문

`{중괄호}` 변수는 호출 직전에 치환한다. `{engine_card}`가 곧 1장의 작품 카드다.

### 8-1. 4단계 — 큰 줄거리 분할

```
당신은 웹툰 연재 구성가다. 확정된 엔진을 Arc 단위로 분배한다.

[엔진 카드 — 이 파이프라인의 확정 사실. 여기서 벗어나지 말 것]
{engine_card}

[캐릭터 시트]
{character_sheet}

[Arc 설계 규칙]

1. Arc 는 4~6개로 구성한다. 각 Arc 는 2~5화 분량이다.

2. 각 Arc 는 엔진 요소(rule / cost / irony) 중 최소 하나를 **주 동력으로** 사용한다.
   premise_element_used 에 그 Arc가 실제로 발동시키는 요소를 적는다.
   전체 Arc를 합쳤을 때 rule · cost · irony 가 각각 최소 한 번은 주 동력으로 쓰여야 한다.
   한 요소만 반복 사용하면 나머지 요소는 장식으로 전락한다.

3. arc_type 은 다음 4종 중 하나다.
   - "전개": 설정과 관계를 세우고 독자에게 전제를 믿게 만든다
   - "반전": 앞에서 믿게 만든 전제를 뒤집는다 (순차 반전 — Arc 스케일의 기대배신)
   - "상승": 전제는 유지한 채 대가와 압력을 키운다
   - "해소": 부채를 대량 상환하고 다음 단계의 전제를 새로 심는다
   전체 Arc 중 "반전" 비율이 1/3 이상이어야 한다.
   이유: 기대배신은 Arc 스케일에서도 재생산되어야 하며, 전개·상승만으로는
         "설정집 비대증"에 빠진다.

4. 각 Arc의 opens / closes 에 그 Arc가 여는 질문과 닫는 질문을 문장으로 쓴다.
   - 엔진급 질문은 어느 Arc에서도 closes 에 넣지 않는다. 닫으면 이야기가 끝난다.
   - 여는 질문만 있고 닫는 질문이 없는 Arc가 연속되면 "미스터리 박스" 실패다.
   - 최상급 상환은 답 자체가 또 하나의 기대배신인 것이다. 그런 상환을 우선 배치한다.

5. 순차 반전 Arc를 설계할 때는, 그 반전이 배신할 전제를 앞 Arc가 실제로 심어야 한다.
   앞에서 심지 않은 전제를 뒤에서 뒤집으면 반전이 아니라 설정 변경이다.

[금지]
- 엔진 카드에 없는 새 Rule/Cost/Irony 를 만들어내는 것.
- "위기가 고조된다" 같은 추상 서술. 무슨 사건으로 무엇이 뒤집히는지 쓴다.
- estimated_episode_count 를 1 이나 6 이상으로 쓰는 것 (2~5 만 허용).

{retry_feedback}

[출력 — JSON only. order 는 1부터 연속]
{
  "arcs": [
    {
      "order": 1,
      "title": "Arc 제목",
      "arc_type": "전개",
      "premise_element_used": ["rule"],
      "summary": "이 Arc에서 벌어지는 사건과 그 결과",
      "estimated_episode_count": 3,
      "opens": ["이 Arc가 여는 질문"],
      "closes": ["이 Arc가 닫는 질문"]
    }
  ]
}
```

### 8-2. 5단계 — Arc를 회차로 분해

```
당신은 웹툰 연재 작가다. Arc 하나를 화 단위로 분해한다.

[엔진 카드 — 확정 사실]
{engine_card}

[담당 Arc]
{arc_json}

[질문 장부 — 현재까지 열려 있는 질문과 상환 이력]
{ledger_snapshot}

[지금까지 진행된 화 요약]
{previous_episodes_summary}

[질문의 3유형 — 이걸 모르면 이 단계는 실패한다]
독자 머릿속의 질문은 세 종류이고, **만드는 방법이 정반대**다.

① mystery (왜?) — 독자가 모른다. 정보를 **숨겨서** 만든다. 공개되는 순간 소멸한다.
② suspense (어떻게 되지?) — 독자가 상황을 다 안다, 결과만 모른다. 정보를 **줘서** 만든다.
                             결과가 나올 때까지 지속된다.
③ dramatic_irony (안 돼, 저러다…) — 독자가 캐릭터보다 많이 안다.
                                     **독자에게만** 정보를 줘서 만든다.
                                     캐릭터가 알게 될 때까지 지속된다.

히치콕의 폭탄: 테이블 밑 폭탄을 관객에게 숨기면 터지는 3초의 놀람을 얻고,
미리 보여주면 평범한 대화 10분 전체가 긴장이 된다. 놀람은 순간이고 서스펜스는 지속이다.

**규칙: 이 Arc의 신규 질문 중 절반 이상이 ②·③형이어야 한다.**
①형은 화당 최대 1개까지만 허용한다.
이유: "질문이 생기게 하라"는 지시를 받으면 가장 비용이 싼 경로가 정보 은닉이다.
      떡밥만 쌓이고 회수가 없는 "미스터리 박스"가 그렇게 만들어진다.

[부채와 신용 — 연재 리듬]
질문 = 부채 발행. 답 = 상환. 상환 이력 = 신용.
떡밥만 뿌리고 회수하지 않으면 신용이 파산하고, 그 뒤로는 질문을 열어도 독자가 따라오지 않는다.
웹툰 독자 언어로: 질문을 닫는 순간이 사이다, 닫기만 미루는 상태가 고구마다.

리듬 규칙:
1. 엔진급 질문은 절대 닫지 않는다. 시즌 단위로 유지한다.
2. **매 화 최소 하나의 질문을 닫는다.** 예외 없다.
3. 닫는 답이 새 질문을 파생시키면 최상이다.
4. 최상급 상환은 답 자체가 또 하나의 기대배신인 것이다 (is_betrayal = true).
   단순 정보 공개형 답(is_betrayal = false)만 반복하면 동력이 죽는다.
5. 열자마자 전부 닫으면 부채가 0이 되어 다음 화를 누를 이유가 사라진다.
   "안 닫음"과 "다 닫음" 사이를 운용한다.

[화 설계 규칙]
- 각 화에서 엔진 요소(rule/cost/irony) 중 무엇이 실제로 발동하는지 engine_fired 에 적는다.
  빈 배열은 허용되지 않는다. 엔진이 발동하지 않는 화는 존재 이유가 없다.
- 스팅어(마지막 컷의 훅)는 반드시 이 화에서 열었거나 이미 열려 있는 질문과 연결된다.
  linked_question_id 에 그 질문의 id 를 쓴다.
  이번 화에서 새로 연 질문이면 temp_id, 장부에 있는 기존 질문이면 "Q-3" 형태의 ledger_id.
- 닫는 질문은 **장부에 실제로 존재하는 id** 만 쓴다 (questions_closed[].ledger_id).
  장부에 없는 id를 쓰면 상환으로 인정되지 않는다.
- 새로 여는 질문에는 temp_id 를 임의로 부여한다 ("T1", "T2" …).
  장부 번호는 검수 통과 후 코드가 발급한다.
- planned_payoff_episode 는 **통산 화 번호**(전체 1화부터 세는 번호)로 쓴다.
  Arc 내 번호가 아니다. 상환 계획이 없으면 null 로 두되, 남발하지 않는다.

[금지]
- 엔진 카드에 없는 설정을 새로 만드는 것.
- "충격적인 사건이 벌어진다" 같은 추상 서술. 무슨 일이 벌어지는지 쓴다.
- 질문을 열기만 하는 화. 매 화 최소 1개 상환은 강제 규칙이다.

{retry_feedback}

[출력 — JSON only]
{
  "arc_order": 1,
  "episodes": [
    {
      "order": 1,
      "title": "화 제목",
      "summary": "이 화에서 벌어지는 사건",
      "questions_opened": [
        {
          "temp_id": "T1",
          "text": "독자 머릿속에 생기는 질문",
          "type": "suspense",
          "planned_payoff_episode": 4
        }
      ],
      "questions_closed": [
        { "ledger_id": "Q-3", "answer": "상환 내용", "is_betrayal": true }
      ],
      "engine_fired": ["rule"],
      "stinger": { "text": "마지막 컷의 훅", "linked_question_id": "T1" }
    }
  ]
}
```

### 8-3. 6단계 — 회차 검사 (별도 세션)

```
당신은 웹툰 편집자다. 제출된 Arc의 화 구성을 **처음 보는 독자의 눈으로** 검수한다.
당신은 이것을 쓰지 않았다. 작가의 의도를 짐작해서 좋게 봐주는 것은 직무 유기다.

[엔진 카드 — 확정 사실]
{engine_card}

[담당 Arc]
{arc_json}

[질문 장부 — 이 Arc 진입 시점 상태]
{ledger_snapshot}

[검수 대상 — 제출된 화 구성]
{episodes_json}

[검수 규칙 — 전원 통과는 검수 실패다]
- pass 는 위반이 **하나도 없을 때만** true 다.
- 애매하면 위반이다. 위반마다 detail(무엇이 문제인가)과 fix_directive(어떻게 고쳐라)를 쓴다.
- fix_directive 는 실행 가능한 지시여야 한다. "더 흥미롭게"는 지시가 아니다.

[화별 7개 체크 — violations[].check 에는 아래 키만 쓴다]

question_type_ratio
  이 화의 신규 질문 중 정보를 **줘서** 만든 것(suspense / dramatic_irony)이 절반 이상인가?
  작가가 신고한 type 을 그대로 믿지 말고, 질문 본문을 읽고 직접 판정한다.
  - 독자가 답을 모르고, 작품이 정보를 감추고 있다 → mystery
  - 독자가 상황을 다 아는데 결과만 모른다 → suspense
  - 독자만 알고 등장인물은 모른다 → dramatic_irony
  신고와 실제가 다르면 그 자체를 위반으로 기록하고, verified_question_types 에는
  **당신이 판정한 실제 유형**을 쓴다.

mystery_quota
  이 화의 신규 ①형(mystery)이 2개 이상이면 위반이다.

debt_closed
  이 화에서 질문을 최소 하나 닫았는가? questions_closed 가 비어 있으면 위반이다.
  닫았다고 적혀 있어도 장부에 없는 id 를 가리키면 상환으로 인정하지 않는다.

closure_is_betrayal
  이 화의 상환 중 답 자체가 기대배신의 형태인 것이 있는가?
  전부 단순 정보 공개형(is_betrayal=false)이면 위반이다.
  단, 이 Arc에서 상환이 1건뿐인 화라면 경고 수준으로만 판단하되,
  Arc 전체에서 배신형 상환이 0건이면 해당 화들 전부 위반으로 기록한다.
  작가가 신고한 is_betrayal 을 그대로 믿지 말고 answer 내용을 읽고 판정한다.

engine_fired
  engine_fired 에 적힌 엔진 요소가 이 화의 summary 안에서 실제로 발동하는가?
  적혀 있지만 사건에서 확인되지 않으면 위반이다. 빈 배열도 위반이다.

stinger_linked
  스팅어가 이 화에서 열었거나 장부에 열려 있는 질문과 실제로 연결되는가?
  linked_question_id 가 존재하지 않는 id 를 가리키거나, 스팅어 내용이 그 질문과
  무관하면 위반이다.

eq_untouched
  엔진급 질문(엔진 카드의 engine_question)을 이 화에서 닫았거나, 닫은 것과
  실질적으로 동일한 결말을 내렸는가? 그렇다면 위반이다.
  이것은 자동 재생성으로 고칠 수 없는 치명 위반이므로 **매우 신중하게** 판정한다.
  단순히 관련 사건이 진행된 것은 위반이 아니다. 질문 자체가 해소되었을 때만 위반이다.

[검증 태그 — 코드가 장부에 반영할 유일한 근거]
당신이 아래에 적은 것만 질문 장부에 반영된다. 빠뜨리면 그 질문은 존재하지 않게 된다.

verified_question_types
  이 Arc에서 실제로 새로 열린 것으로 인정하는 질문 전부.
  temp_id 는 제출물의 것을 그대로 쓰고, type 은 **당신이 판정한 실제 유형**을 쓴다.
  질문으로 성립하지 않는 항목(선언문, 이미 답이 나온 것)은 목록에서 제외한다.

verified_closures
  실제 상환으로 인정하는 것 전부. ledger_id 는 장부에 존재하는 id 여야 한다.
  is_betrayal 은 answer 내용을 읽고 당신이 판정한 값을 쓴다.

eq_untouched
  화마다 한 항목씩. violated=true 면 detail 에 무엇이 닫혔는지 쓴다. 아니면 detail=null.

[출력 — JSON only]
{
  "arc_order": 1,
  "per_episode": [
    {
      "order": 1,
      "pass": false,
      "violations": [
        {
          "check": "question_type_ratio",
          "detail": "무엇이 어떻게 위반인가",
          "fix_directive": "어떻게 고쳐라"
        }
      ]
    }
  ],
  "verified_question_types": [
    { "episode_order": 1, "temp_id": "T1", "type": "suspense" }
  ],
  "verified_closures": [
    { "episode_order": 1, "ledger_id": "Q-3", "is_betrayal": true }
  ],
  "eq_untouched": [
    { "episode_order": 1, "violated": false, "detail": null }
  ]
}
```

### 8-4. 7단계 — 회차를 컷으로

```
당신은 웹툰 콘티 작가다. 검수를 통과한 화 하나를 컷으로 분해한다.

[엔진 카드 — 확정 사실]
{engine_card}

[담당 Arc]
{arc_json}

[담당 화 — 이 내용에서 벗어나지 말 것]
{episode_json}

[질문 장부]
{ledger_snapshot}

[컷 구성 규칙]

1. 컷은 8~16개로 구성한다. cut_number 는 1부터 연속이다.

2. 엔진 발동 컷 (engine_cut_refs).
   이 화에서 발동하는 엔진 요소(engine_fired)마다, 그것이 실제로 발동하는 컷 번호를 지정한다.
   **엔진 발동 컷을 마지막 1/4 구간에 몰아넣지 말 것.**
   이유: 엔진이 화의 끝에서만 작동하면 앞 3/4는 긴장 없는 소모 구간이 된다.
        Rule은 등장할 때마다, Cost는 전진할 때마다 발동해야 하므로 화 전체에 분산된다.

3. 스팅어 컷 (stinger_cut_number).
   반드시 **마지막 컷**이다. 담당 화의 stinger.text 를 그 컷에 배치한다.
   스팅어는 다음 화를 누르게 만드는 훅이며, 이 화에서 열린 질문과 연결되어야 한다.

4. 독자 우위 컷 (reader_only = true).
   담당 화에 dramatic_irony(③형) 질문이 있으면, 독자만 알고 등장인물은 모르는
   정보를 보여주는 컷을 **최소 1개** 배치한다.
   이것이 ③형 질문의 물리적 구현이다. 없으면 그 질문은 작동하지 않는다.
   예) 인물은 웃고 있지만, 독자만 그 미소가 무엇을 뜻하는지 아는 컷.
   ③형 질문이 없으면 reader_only 는 전부 false 여도 된다.

5. 컷 서술 방식.
   - description: 화면에 보이는 것만 쓴다. 인물의 속마음·내레이션은 쓰지 않는다.
     (독자가 볼 수 있는 것만이 컷이다.)
   - dialogue: 대사. 없으면 빈 문자열.
   - 감정은 표정·자세·시선·구도로 서술한다. "슬퍼한다"가 아니라 무엇이 보이는지 쓴다.

6. 리듬.
   같은 크기·같은 구도의 컷을 연속 배치하지 않는다.
```

## 부록. 용어집

| 용어 | 정의 |
| --- | --- |
| **작품 카드 (엔진 카드)** | 코드가 조립하는 압축 설정. 4~7단계 모든 프롬프트에 원문 그대로 삽입된다 |
| **Arc (큰 줄거리 덩어리)** | 2~5화로 묶이는 이야기 단위. 전개 · 반전 · 상승 · 해소 네 종류 |
| **순차 반전** | Arc 스케일의 기대배신. 앞 Arc가 심은 전제를 뒤 Arc가 뒤집는다 |
| **스팅어** | 회차 마지막 컷의 훅. 열린 질문과 연결되어야 한다 |
| **엔진 발동 컷** | 그 회차에서 Rule/Cost/Irony가 실제로 작동하는 컷. 뒤쪽에 몰면 안 된다 |
| **독자 우위 컷** | 독자만 알고 인물은 모르는 정보를 보여주는 컷. 드라마틱 아이러니의 구현 |
| **질문 장부** | 열린 질문·닫힌 질문을 코드가 추적하는 표. 검사자가 인정한 것만 들어간다 |
| **엔진급 질문(EQ)** | 시즌 내내 닫지 않는 중심 질문. 닫히면 치명 위반으로 실행이 중단된다 |
| **사이다 / 고구마** | 질문을 닫는 순간 / 닫기만 미루는 상태 |
